# ADR 0006: Durable native AP2 authority for embedded ACP admission

Status: proposed for independent review, 2026-11-07. This decision extends [ADR 0005](0005-independent-ap2-engine.md) with a bounded local synthetic composition. Acceptance requires the implementation and evidence below; this document alone does not enable an external bridge.

## Context and scope

The independent `ap2-v0.2-direct-tap-synthetic-0.1` engine already verifies native closed mandates, merchant checkout signatures and signer-purpose trust. Its `authorize*` methods consume process-local replay state, which cannot participate in the PostgreSQL financial transaction. The current `JdbcPaymentStore` serializes commands and worker admission on the authenticated `(tenant, run)` row. Approval creates the sole attempt and budget reservation; execute persists the sole operation/outbox; dispatch admission is a later ordered transaction before the effectful adapter send. Preserve those boundaries.

The user additionally requires every component boundary to support independently replaceable, composable implementations. New backends require an adapter and trusted registration, not a new vendor-specific interface or a caller/core/workflow change. Apply this versioned behavioral-contract rule to protocol, orchestration, authentication/identity, provider execution, events, trust, artifact storage and admission boundaries. A concrete adapter or library is not the contract; a wrapper alone does not establish compatible behavior.

Implement a separately selected composition profile, `local-ap2-acp-single-tender-0.1`, while retaining the explicit `local-fake-single-tender-0.1` fixture profile. The former encloses an immutable ACP checkout and independently verified native AP2 authority inside PaymentIntent. Both use the existing synthetic-card simulator adapter and `simulator-core` execution owner. A composition-profile identifier is not a new provider capability. A failed native check never falls back to local-fake approval.

AP2 remains pinned to v0.2.0 commit `b4587ac1d055888a73b4b21750973cffba961793` and the exact direct-TAP profile in ADR 0005. ACP remains the researched `2026-04-17` schema directory at commit `7fdd78df677a94dce04c770644b0fbbb1401272b`, with checkout-schema SHA-256 `d0e4290617d66bf05d002b8ace388732be2b3eb9a92a1003db7a2daa1e0436f2`. [Source lock](../../integrations/upstream/source-lock.json) and [bridge research](../ap2-acp-bridge-design.md) retain the provenance. Do not select mutable upstream code, copy Google's protocol implementation, or introduce a crypto/framework dependency.

This is a fixture merchant/TAP/CP/processor composition with local synthetic identity and approval. It supplies no network ACP merchant transport, authenticated external AP2 peer, negotiated sidecar, production user identity, provider credential, live payment, broader delegation or full AP2/ACP interoperability. In particular, ACP has no native AP2 mandate field in the selected complete request; storing the relationship internally does not create an interoperable wire extension.

## Replaceable component contracts

Each genuine component boundary has one stable responsibility-based contract with immutable version identity, typed inputs/outputs, declared capabilities, ownership, clock/idempotency semantics, bounded failures and a reusable behavioral test suite. This applies equally to the existing payment adapter, authenticated-session resolution, graph/payment-client, verified-event and trusted-action boundaries. Extend an established port when its responsibility matches; do not create interfaces for private helpers or vendor names. Azure, Dynamo, Stripe or a payment-grant service are possible adapters, not interface categories. A payment-grant service implementing immutable artifact retention can implement the same artifact-store port; one implementing atomic financial admission can implement that distinct responsibility's port. A new backend adds an implementation and trusted registration, with no core/application/workflow change when it satisfies the contract.

Wrapping and delegation are explicit composition modes. A decorator may add policy, telemetry, storage or routing while preserving exact artifacts, idempotency, error meaning and financial ownership. It cannot turn rejection into acceptance, relax the selected profile or hide uncertain outcomes. A delegating adapter declares who owns checkout state, signature verification, artifact retention, grant admission and the effectful send. Preserve provenance and intersect effective capabilities through wrappers. Unknown required capabilities, conflicting owners or an incompatible version fail before creating authority or exposure. The execution-owner decision is immutable for an attempt; switching adapters after timeout cannot create a second send.

The following logical ports are required. Java names may follow existing conventions; responsibilities and trust boundaries are fixed:

| Versioned port | Behavior and security contract | Reference and replacement |
| --- | --- | --- |

Include exact payload/reference, merchant/session/revision, protocol/version, selected handler/instrument, money, expiry and provenance. Extract/compare facts under the closed profile; caller totals or `ready=true` are not authority. | Independently authored ACP `2026-04-17` fixture adapter. Contract values are immutable and defensively copy arrays/JSON; errors and string representations redact sensitive facts. Expected facts come from authenticated server configuration and durable state. Implementations are trusted composition-root registrations, never caller/model/plugin-document requests. Conformance tests and capability checks are prerequisites, not protection against malicious trusted server code.

Application contracts import no concrete AP2/ACP engine, JCA, Azure, Dynamo, Stripe or JDBC type. Independent protocol engines may depend on crypto/trust ports, not payment storage. Internal JDBC helpers may share a connection; that detail cannot become a public port parameter. Avoid a generic service locator or interfaces for each private function. Keep the independently authored protocols useful outside the PostgreSQL reference platform.

### Concrete port shape

The following implementation-neutral signatures fix the call directions. Records contain the typed fields specified above; implementation names and Java/Python packaging can follow existing conventions. They are responsibility contracts, not vendor variants:

```text
CheckoutProtocol.describe() -> ContractDescriptor
CheckoutProtocol.freeze(CheckoutRequest) -> FrozenCheckout
CheckoutProtocol.validate(FrozenCheckout, ExpectedCheckout, VerificationTime) -> CheckoutFacts
AuthorityVerifier.describe() -> ContractDescriptor
AuthorityVerifier.verify(AuthorityRequest) -> VerifiedAuthority
AuthorityIssuer.issue(IssuanceRequest) -> IssuedAuthority
SignatureProvider.describe() -> ContractDescriptor
SignatureProvider.sign(Suite, SigningKeyHandle, OriginalBytes) -> SignatureBytes
SignatureProvider.verify(Suite, PublicKeyBytes, OriginalBytes, SignatureBytes) -> verified/rejected
KeyResolver.resolve(TrustScope, ExpectedIssuer, Kid, Purpose, VerificationTime) -> TrustKey
SignedArtifactStore.put(ArtifactScope, ImmutableArtifact) -> ArtifactReference
SignedArtifactStore.get(ArtifactScope, ArtifactReference, ExpectedDigest) -> ImmutableArtifact
```

`ContractDescriptor` includes contract/version, supported profile/capabilities, owner/composition mode and implementation provenance. `FrozenCheckout` contains immutable exact artifacts/references and authoritative session/revision/profile/merchant metadata; `CheckoutFacts` contains validated payee, currency/minor units, instrument/handler and expiry. `ExpectedCheckout` comes from the trusted catalog/configuration, never the returned object alone. `AuthorityRequest` contains exact mandate/checkout artifacts, trusted expected checkout facts, subject/grant issuance association, role-specific issued challenges, selected profile/time and enrolled trust. `VerifiedAuthority` contains authenticated role/issuer/JWT-ID identities, artifact digests and effective expiry; only the application-owned verification call in the admission pipeline can supply it to transaction internals. `IssuanceRequest` fixes the same facts plus authorized key handles; its output is untrusted until independently verified. `Suite` is a preselected allowlisted identifier, and public key bytes use a specified standard encoding; concrete JCA key objects do not enter this contract. `ImmutableArtifact` fixes bytes, media/profile, bounded length and content digest. `ArtifactReference` fixes scope and immutable identity; stringification redacts it where sensitive.

Reuse the existing aggregate `PaymentStore`/application boundary for atomic grant admission rather than introduce independent reserve/replay CRUD ports. Its declared admission capability covers current-grant checks, replay consumption, reservation, attempt and accepted response in one ordered unit of work. A replacement implementing this same responsibility cannot split it into uncoordinated backend calls. Internally transaction-scoped artifact/trust adapters may share the reference connection without exposing it through any signature above.

### Durable workflow runtime

The same replacement rule applies to execution of the LangGraph workflow. Separate reusable payment decision logic and typed activity/signal definitions from one stable runtime lifecycle contract; adapters provide durable start/resume, signals, timers, activity retry, cancellation and recovery according to declared capabilities. The detailed contract and implementation decision belong to [ADR 0007](0007-durable-workflow-runtime.md), authored and reviewed separately. New runtime backends must require only an adapter and trusted registration when they satisfy that contract, without rewriting protocol or business-workflow logic.

Persist tenant/run/workflow and definition-version identities and preserve payment command identities across activity retries. Runtime status/history is orchestration evidence, never payment truth. Trusted-approval/authentication signals wake the graph to read current core state; signal payloads cannot establish consent or financial outcomes. Cancellation cannot declare an admitted payment cancelled or release UNKNOWN exposure. Recovery after response loss reads status and reconciles the original operation.

The runtime boundary must distinguish deterministic decisions from effects. An engine with deterministic history replay must integrate graph execution through its reviewed activity/decision contract; it cannot blindly replay HTTP, model calls, time or randomness inside a deterministic workflow callback. The current LangGraph/SQLite implementation proves checkpoint persistence and explicit restart/resume only, not automatic scheduling, durable timers or a Temporal/Cadence/Azure Durable Task connector. Required capabilities and supported reference implementations are fixed by ADR 0007; this ADR does not pre-approve an unreviewed engine adapter.

Required integrated demonstration: agent checkout, trusted approval, synthetic authentication pause, crash/restart, resume and reconciliation of the same operation, with only safe references in runtime state. Behavioral runtime replacement/decorator evidence belongs to the separately reviewed runtime slice; the payment binding must remain invariant through it.

### Artifact storage and atomic admission

Artifact retention and admission have different consistency requirements. The reference may store artifacts in the same PostgreSQL transaction, but the artifact-store contract must also support independent immutable staging. Stage bounded exact bytes before admission, verify references/digests, then atomically commit their references, authority binding, replay consumption, reservation, attempt and command result inside the admission owner. A failed admission may leave an unreferenced immutable artifact; it never leaves spend authority. Cleanup cannot delete referenced artifacts or recycle their identities. Signing/staging success is not approval.

At approval and pre-dispatch verification, load exact referenced bytes and check digest/length/profile and the immutable association before accepting authority. Missing, altered or unavailable artifacts prevent new admission. Transient unavailability after admission cannot fabricate cancellation/no-effect or release exposure. Immutable bytes may be prefetched outside the transaction; recheck their references/digests and authoritative versions under the admission lock. External I/O cannot silently release that lock or change the expected facts.

Calling a remote grant service inside JDBC does not make it atomic with PostgreSQL. A replacement must share the admission unit of work or implement a reviewed fencing/reservation/commit/recovery protocol ordering grant revocation, replay, budget and attempt ownership. The slice implements only the PostgreSQL atomic capability. An independently committing grant/replay/budget composition fails `UNSUPPORTED_CAPABILITY` before reservation. Azure/blob storage, DynamoDB and PostgreSQL are not claimed to jointly commit atomically. An external ACP replacement likewise needs a reviewed freeze/version-CAS or equivalent completion agreement preventing merchant updates racing an approved snapshot. In-process replacement/decorator tests prove contracts, not that a live Stripe merchant provides these guarantees.

Minimum extension evidence includes behavioral replacement/decorator/delegation tests for checkout, authority, signature/key and artifact-store ports, plus rejection of an incompatible independently committing admission backend. Verify exact snapshot/mandate/attempt binding across replacements, capability intersection through wrappers, fail-closed unsupported algorithms and storage-staging faults with no reservation. Simply constructing two implementations is insufficient.

Keep the existing create, quote, checkout, approve and execute routes and closed request bodies. Extend create's profile enum deliberately; persist it on the intent and return the actual selected value in status. Quote and approve branch by that persisted profile, never by a caller-supplied verification flag. Quote still accepts only configured cart/tender fixture references. Approve retains `expectedVersion`, `checkoutRevision`, `checkoutDigest`, `authorityReference`. Existing graph sessions cannot approve, choose signer keys, register challenges, revoke authority or obtain raw artifacts. Existing trusted UI reads the current server-owned checkout and displays its merchant, money and revision before approval.

The local native path needs an injected trusted fixture-signing/issuance boundary for tests. Tests can supply independently generated signed mandates or faulting signers through that internal boundary. The production HTTP surface accepts no raw mandate, public key, audience, nonce, caller amount, arbitrary checkout JSON or callback URL. Test injection does not bypass signature, content, scope or replay checks and must not be reachable from a bearer request. Unsupported raw inputs fail the existing closed-schema validation.

## Authoritative embedded checkout

The reference checkout-protocol adapter constructs a closed, supported ACP `CheckoutSession` from the immutable fixture catalog and registered merchant/handler configuration. The application invokes its port and validates the selected negotiated profile. Validate `protocol.version`, unique server-owned session identity, `ready_for_payment`, EUR/USD currency, exactly one positive integer final total, matching line-item allocation, configured fulfillment, expiry and the complete selected handler/instrument configuration. No FX, mixed merchants, delegation, arbitrary URLs or schema fetching is permitted. The native ACP fixture shape must pass the exact pinned upstream schema in contract tests; runtime construction and validation enforce the narrower allowlisted profile. Do not claim a general ACP schema engine from this fixture constructor.

Persist exact UTF-8 ACP JSON bytes and the exact compact merchant ES256 checkout JWT through the artifact-store boundary for every immutable revision; authoritative rows retain immutable references/digests. The JWT payload is the unchanged ACP object, with no invented AP2 or project revision properties inserted into it. Persist project revision, tenant/run/intent, merchant identity, ACP session ID, handler, instrument, quote expiry and expected payee separately. Verify the merchant signature and equality of the decoded payload to the frozen ACP bytes. Randomized re-signing over identical payload creates a different authorization identity and cannot silently replace the frozen JWT.

For this profile, public `checkoutDigest` retains its `sha256:<64 lowercase hex>` representation but hashes the exact ASCII merchant JWT. Native `checkout_hash` and payment `transaction_id` encode the same digest bytes as 43-character unpadded base64url, with no prefix. The old local-fake profile retains its documented local-checkout canonical-byte digest. Never compare these strings as if their encoding or input domain were interchangeable. The native row retains immutable references to the exact original artifacts and explicit profile/revision, not only a parsed JSON object or hash.

Requote creates a new immutable revision while the intent is DRAFT/QUOTED. Approval binds only the current revision. No approved attempt can be requoted or have its snapshot, payee, handler or instrument replaced. The existing one-attempt-per-intent rule remains.

## Trusted identity, key and issuance binding

The API session is authentication to the local platform, not an AP2 mandate. Trusted approval must match the existing grant's subject, merchant, allowed grant, budget currency, validity and version under the transaction lock. Fixture TAP issuance derives all signed fields from that authorized session, the current grant and the frozen checkout. The native closed profile has no subject claim: therefore a durable issuance record is the explicit trusted association between the TAP issuer/key, exact mandate pair and authenticated subject/grant/version. Never infer a subject from an arbitrary signature or add an undocumented native claim.

The reference key/trust adapter persists public P-256 verification keys and their exact issuer/kid/purpose, valid-from/until, revoked state and configuration version under authenticated tenant/run scope. Merchant-checkout, TAP-checkout, TAP-payment-for-CP and TAP-payment-for-MPP permissions remain distinct even if a fixture key is intentionally permitted for more than one purpose. Expected issuer, merchant and audience come from server configuration and issuance rows; untrusted JWT headers only select a previously enrolled `kid`. No embedded/remote key establishes trust. The internal provisioning path is unavailable to graph/UI roles.

The reference signer generates private synthetic keys in memory and never serializes, logs or commits them. Replacement signers expose opaque handles, not private bytes to application code. A restarted service can verify and execute an existing approved attempt using persisted public trust and exact artifacts, without re-signing or re-issuing them. New quotes/approvals after restart provision fresh unique fixture key IDs and persist their public permissions; existing records retain their original key IDs. Never overwrite old key material under an existing issuer/kid/purpose. Lack of a usable signer safely blocks new issuance, not reads or reconciliation. Provisioning and trust revocation must use the same run transaction lock as approval/admission; key revocation is monotonic and an internal runner/test capability in this slice, not an external enrollment API.

The server issues unpredictable challenge identities, with separate merchant and shared CP/MPP payment audience/nonce contexts. CP and MPP verify the Payment Mandate independently and consume distinct role namespaces. Challenges bind tenant/run, intent, current revision and checkout hash, subject, grant/version, expected TAP issuer, exact audience and deadline. They must be established by trusted issuance before verification; the submitted artifacts cannot redefine them. Issuance and initial challenge insertion may occur within the same approval transaction because no external peer transport exists. Each challenge expires within 300 seconds and no later than the grant and checkout; the signed mandates obey all ADR 0005 time constraints.

## Durable model and transaction

Add a new versioned migration after V006; do not edit checksummed earlier migrations. Use explicit column lists when altering tables whose current inserts use positional `VALUES`. Preserve old records using an explicit legacy profile default, rather than treating absent native evidence as successful native verification.

The normalized model must represent these logical records; physical names may follow existing repository conventions:

| Record | Required binding and constraint |
| --- | --- |
| Intent profile | Immutable selected composition profile; existing rows default to the old profile. |
| Native checkout | Unique `(tenant,run,intent,revision)` FK to checkout snapshot; immutable ACP/JWT artifact references and digests, session, both hash encodings, merchant/payee/handler/instrument and expiry. |
| Public trust | Unique scoped issuer/kid/purpose with original public key bytes, validity, version and monotonic revocation. |
| Issuance/authority | Immutable references to exact Checkout and Payment Mandates, their hashes, subject/grant/version, current checkout FK, signer identities, challenge contexts, effective expiry and sole attempt FK. Uniqueness prevents an artifact pair from being attached to another attempt. |
| Issued challenge | Unique scoped role/nonce and immutable expected transaction/issuer/audience/subject bindings; durable consumed-by-attempt marker or equivalent consumption FK. |
| Replay identity | Unique `(tenant,role,issuer,jti)` across runs, recording the consuming run/attempt. Do not include principal, nonce, audience, key ID or signature in the uniqueness predicate; these cannot be aliases that permit reuse. Role separation permits CP and MPP to consume the same payment identity independently. |

Every persisted reference that resolves payment state must include tenant/run and immutable parent identity; enforce the corresponding composite foreign keys. Retain replay identities, exact authority records and command identities for the run's supported lifetime; do not recycle them on expiry, restart, cancellation or failed later execution. Tenant-wide replay uniqueness additionally serializes conflicting cross-run insertions through PostgreSQL even though different runs have separate row locks.

For native approval, perform the following within the existing `command()` transaction holding the run row lock:

1. Authorize the current caller before replay lookup; validate command identity/digest. An accepted identical command returns its historical safe response. A changed request under that key conflicts.
2. Lock/read the current intent, profile, checkout, grant, budget and public-trust versions. Validate role/object/subject scope, expected version/revision/digest, exact money, current authority and available capacity.
3. Create or load the trusted fixture issuance and challenges. Invoke the issuer/signer ports with trusted expected facts. Re-read exact signed bytes through the configured independent authority verifier; signing is not verification. The reference shares the artifact transaction; independently staged artifacts must have all expected versions/challenges rechecked under this lock.
4. Independently verify merchant Checkout Mandate plus embedded checkout signature and native Payment Mandate under both CP and MPP trust purposes. Compare complete payee, integer money/currency, instrument, exact checkout JWT/hash, issuer, audience, nonce and validity. Use the same transaction clock for all roles. Inspect authenticated identities only after verification.
5. Consume all three issued challenges and insert all three role-specific issuer/JWT-ID replay identities. Any missing/mismatched/already-used identity fails the entire transaction. The in-process CP `CredentialBinding` is not serialized as financial authority; the durable complete CP/MPP scope binding replaces that offline object at this infrastructure boundary.
6. Persist the immutable native authority record bound to the sole attempt, create the reservation, increase budget held, set APPROVED, write audit and save the safe command response. Commit them together. No effectful payment-adapter call occurs within this transaction.

A signature error, budget failure, conflict, storage fault or process crash before commit leaves no accepted authority, consumed replay identity, reservation, attempt or command response. Independent artifact storage may retain only unreferenced immutable staging, which grants no authority. No partial CP consumption survives an MPP failure. Concurrent same-key requests converge on the original result; concurrent different-key approvals cannot create a second attempt. Unique constraints are required even when application locking appears sufficient.

## Execution, revocation and recovery

Execute keeps its existing operation/outbox transaction and one adapter key. For native attempts, reconstruct expected facts from the exact persisted authority/checkout and validate current grant version, signer permissions, snapshot binding and effective expiry before queuing preparation. Preparation remains effect-free. Immediately before effectful DISPATCH, independently verify the persisted native artifacts again against current public trust and the transaction clock, and check the same authority/checkout/grant binding plus the HELD reservation and required trusted action. Read-only re-verification never consumes replay identities again; it checks that their durable consuming attempt is this attempt. A cached process-local proof cannot replace this gate.

Effective authority expiry is the minimum of checkout, grant, issued challenges and both mandate expiries. Key validity/revocation is checked at the current gate as well. Native expiry can therefore be earlier than the existing 900-second fixture quote. No silent renewal, fresh nonce, re-signing or substitution can extend an approved attempt. Expired/revoked/invalid native authority before admission cancels or expires the attempt under the existing no-effect termination rules and releases held exposure exactly once. It does not remove consumed replay identities. Reverification/storage failures must never permit dispatch; infrastructure uncertainty retains state for retry rather than asserting financial no effect.

Grant and key revocation are ordered by the same run lock as DISPATCH admission. Revocation winning that order prevents new admission. A committed admission winning the order remains admitted even if the process dies before the send; revocation cannot assert cancellation or release its exposure. Existing reconciliation/adapter idempotency identifies the same operation, and the implementation must preserve existing admitted journal recovery behavior. Do not use newly expired/revoked AP2 authority to suppress necessary reconciliation of an already admitted operation or to create a replacement operation.

The admission row retains its existing timestamp, admission sequence and grant version, plus the immutable native authority association through its attempt. Operation request binding must include the exact native checkout digest and attempt/authority identity (directly or through an unambiguous immutable attempt FK); no later checkout can change the adapter request. Outcome evidence remains simulator-owned. Authorization, ACP `ready_for_payment`, browser completion and AP2 receipt verification are not payment success.

## Signing failures and receipts

Merchant checkout and TAP mandate signing precede financial approval commit. Failure produces only a fixed safe unavailable/invalid-authority result and rolls back dependent mutations. An accepted command retry returns its stored result and does not invoke the signer again. Signing is not needed to recover accepted artifacts or an existing operation.

No new receipt API is required for this slice. The independent engine's offline typed receipt exchange remains available as its own tested profile. Do not feed its synthetic processor authorization Success receipt into the financial evidence path. A bridge Payment Receipt Success, if later implemented, must follow authoritative operation success and name actual synthetic simulator confirmations, not fabricated evidence at approval. Receipt signing failure after committed authorization/admission must be represented as `receipt_unavailable` without turning acceptance into rejection, reopening replay or releasing exposure. Receipt retrieval/recovery cannot create another payment. The current slice must not claim a newly implemented end-to-end native receipt transport.

## Errors, privacy and validation

Use existing safe API error conventions: unauthorized scope is 404, role denial 403, unsupported profile 422, changed checkout/version 409, native content/signature/scope mismatch 422 `AUTHORITY_BINDING_INVALID`, expired authority 410, revoked authority 409, replay 409 with a documented fixed code, and signing/storage unavailability 503 `TEMPORARILY_UNAVAILABLE`. Command retry instructions preserve the original key. Do not expose parser text, compact tokens, keys, ACP bodies or sensitive expected facts in responses, exception messages, object string representations, reports or graph checkpoints.

Raw synthetic ACP/JWT/mandate artifacts are intentionally persisted only behind the trusted artifact-store boundary (the reference uses PostgreSQL); this differs from the isolated offline sidecar's metadata-only storage. No bearer token, private key, real payment credential or OTP is stored there. Public HTTP results, commands response JSON, safe audit evidence and LangGraph state use only their allowlisted references, digests, versions, profile, money and state. Fixture-only database persistence supplies neither production encryption/retention policy nor permission to ingest real credentials.

Acceptance requires real PostgreSQL integration and cross-language/native-engine regression evidence, including:

- Successful native quote, trusted approval, restart, execute, synthetic action, admission and outcome with the exact immutable authority/checkout linkage; separately selected legacy flow still passes.
- Independently signed wrong checkout revision/bytes, equal JSON with a new signature, wrong payee/money/instrument, role/key/issuer/audience/nonce, future/expired mandate, unknown claims and unsupported profile all reject without reservation or replay mutation.
- Signer and SQL faults before commit, capacity failure and CP-success/MPP-failure leave no partial attempt/consumption. Retry after a lost accepted response or process restart returns the same attempt and operation, without re-signing.
- Concurrent duplicate commands and different-key approval races yield one reservation and attempt. Reusing issuer/JWT-ID with another valid signature, nonce, key, principal, intent or run cannot bypass durable replay; role-separated CP/MPP verification remains valid.
- Requote invalidation, cross-tenant/run/principal/grant substitution, key rotation after restart, persisted old-key verification, key/grant revocation races, expiry before dispatch and admitted recovery after revocation have explicit outcomes.
- A response-loss/UNKNOWN case keeps exposure and reconciles the original adapter key. Native verification or signed receipts alone never consume/release budget or produce SUCCEEDED.
- The separately reviewed runtime contract preserves workflow/definition/payment-command identities and the core authority boundary across restart. ADR 0007 owns runtime-specific replacement, scheduling and deterministic-replay acceptance evidence.
- HTTP/TypeScript schemas and LangGraph profile selection/status validation pass. Graph SQLite restart/resume performs no second execute, and persisted checkpoints/reports contain no raw artifacts or signing material.
- Alternate/decorated checkout, authority, signature/key and artifact-store implementations pass reusable contract tests. Incompatible admission atomicity and unsupported suites fail closed; staging faults leave no reservation and post-admission storage failures preserve reconciliation.
- The emitted ACP fixture payload validates against the pinned upstream schema, and independent native AP2 vectors still pass. Evidence names this local composition profile and preserves all excluded wire/provider/conformance obligations.

Run the repository documentation, diff and complete conformance gates after implementation. Versioned migrations require restart and old-schema upgrade coverage. No live network/provider test, new framework, vendor SDK import, automatic deployment or certification claim is part of this decision.
