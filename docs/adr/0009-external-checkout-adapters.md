# ADR 0009: Add a bounded external checkout lifecycle adapter

## Status

Accepted for the bounded reference profile described below. See the platform guides and executable tests for current implementation limits.

## Context and bounded outcome

The product must support independently replaceable AP2 and ACP implementations, including an independently authored ACP implementation that delegates to another checkout service. An adapter must implement a responsibility contract rather than expose a vendor SDK as the application interface. The current native `CheckoutProtocol` freezes and validates a locally signed merchant checkout. Its methods run inside the JDBC transaction/run lock. It is not an outbound merchant-session transport contract, and substituting an HTTP client there would introduce blocking network I/O under the financial lock.

The smallest useful next slice is a standalone checkout lifecycle contract and an outbound HTTP implementation for the already selected ACP `2026-04-17` snapshot. Prove create, retrieve, update and cancel against an independently authored loopback peer. Do not add completion, payment delegation, authentication delegation, provider execution, AP2 issuance or native financial wiring. This is transport/commerce evidence, not a usable external AP2/ACP financial composition, vendor interoperability, broad ACP conformance or certification.

An HTTP adapter can be implemented without account access. A real PSP sandbox adapter cannot truthfully fit the existing synthetic-only payment SDK without separately reviewed contract evolution. That feasibility decision is recorded below rather than hidden behind a simulator implementation bearing a provider name.

## Exact source and wire contract

Normative inputs are the existing [source lock](../../integrations/upstream/source-lock.json), `acp-spec-2026-04-17-openapi-openapi-agentic-checkout-yaml` artifact at path `spec/2026-04-17/openapi/openapi.agentic_checkout.yaml`, and `acp-checkout-schema` at commit `7fdd78df677a94dce04c770644b0fbbb1401272b`. The OpenAPI SHA-256 is `2a0aa239b4aed50732461d9b7e443ad98d5c2d3431277899433ead07cbd4fc55`; verify locked length, SHA-256 and Git blob identity before using cached source bytes. No upstream implementation or SDK is imported, wrapped or copied into the protocol engine.

The immutable [OpenAPI contract](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/blob/7fdd78df677a94dce04c770644b0fbbb1401272b/spec/2026-04-17/openapi/openapi.agentic_checkout.yaml) and [JSON Schema](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/blob/7fdd78df677a94dce04c770644b0fbbb1401272b/spec/2026-04-17/json-schema/schema.agentic_checkout.json) govern this slice. The mutable [official OpenAI checkout documentation](https://developers.openai.com/commerce/specs/checkout), inspected on 2026-11-08, remains a different, older surface using `items`; it does not override the selected snapshot or establish deployed peer support. Real-peer version and access agreement remains required.

| Operation | Exact request | Expected successful response |
| --- | --- | --- |
| Create | `POST /checkout_sessions`, JSON `CheckoutSessionCreateRequest` | HTTP 201, `CheckoutSession` |
| Retrieve | `GET /checkout_sessions/{checkout_session_id}`, no body | HTTP 200, `CheckoutSession`; HTTP 404 is not found |
| Update | `POST /checkout_sessions/{checkout_session_id}`, JSON `CheckoutSessionUpdateRequest` | HTTP 200, `CheckoutSession` |
| Cancel | `POST /checkout_sessions/{checkout_session_id}/cancel`, no body in this profile | HTTP 200, `CheckoutSession`; HTTP 405 is not cancelable |

Create requires `line_items`, `currency` and `capabilities`. Its closed `Item` schema declares `id`, optional `name` and optional `unit_amount`; it does not declare `quantity`. The first profile therefore creates item references with `id` only, lowercase `usd` or `eur`, and `capabilities: {}`. The minimum conforming body is `{"line_items":[{"id":"synthetic-item"}],"currency":"usd","capabilities":{}}`. No `items`, `product_id`, `quantity`, provider token, AP2 mandate or invented metadata binding is added. Update supports replacement `line_items` containing these same item references only; it does not add currency or capabilities fields, which that request schema does not declare. Decline unsupported buyer, fulfillment, discounts, attribution, extension and intervention inputs explicitly rather than silently discarding them. The minimal profile advertises none of those capabilities.

Schema constraints take precedence over contradictory examples. Preserve negative probes for obsolete `items` and unsupported `quantity`; the selected examples are not an alternate wire profile. Response `protocol` is optional in the pinned schema. If present, its version must equal `2026-04-17`; absence is not silently filled in as peer evidence. The configured exact profile selects the request version, but neither that configuration nor a matching field proves real-peer acceptance.

Send `Authorization: Bearer <trusted peer credential>` and `API-Version: 2026-04-17` on every request. Every POST includes caller-supplied `Idempotency-Key`, length 1..255, scoped to authenticated peer identity and exact endpoint; no generated replacement key is permitted during retry. Use an optional bounded opaque `Request-Id` for correlation, an honest project `User-Agent`, `Accept: application/json`, and `Content-Type: application/json` for JSON bodies. GET has neither request body nor required POST idempotency header. Cancel sends an absent body consistently, preserving that representation for retries.

`Accept-Language`, `Request-Id`, `User-Agent`, `Signature` and `Timestamp` are optional in the pinned OpenAPI. Its `Signature` description refers to an HMAC webhook signature without defining this client's signing transcript, algorithm or enrollment. This profile does not fabricate a signature or claim request-signature support. A peer requiring signing is unsupported until a separately reviewed signing profile exists. No ChatGPT user agent, OpenAI identity or partnership is impersonated.

## Responsibility boundary and implementation

Add one protocol-neutral `CheckoutSessions` responsibility contract, version `1`, with explicit `create`, `retrieve`, `update` and `cancel` methods, immutable values, a descriptor and typed failures. A concrete `AcpHttpCheckoutSessions` implementation owns ACP request encoding, endpoint mapping, HTTP and response decoding. Native, delegated and decorated implementations can implement the same contract. Do not add a separate interface for each merchant/provider or reuse `PaymentAdapter` for commerce-session operations.

The bounded contract contains:

- Trusted peer binding: caller tenant/principal authorization scope, enrolled merchant identity and adapter configuration identity. An untrusted request cannot choose a base URL, bearer token, signing key or principal. The binding is not serialized into invented ACP fields.
- Item references and exact supported currency for create; replacement item references for update. An immutable command identity contains the caller's idempotency key and stable correlation reference. Retrieve and cancel use a session handle carrying its original trusted peer binding.
- A protected checkout document preserving exact response bytes, plus a bounded projection of session identity, lifecycle status and an optional observed protocol version. The document is not a `FrozenCheckout`, `VerifiedAuthority`, provider `Fact` or proof of payment. Its string representation, failures and public diagnostics redact document/header/credential values.
- A typed result retaining numeric HTTP status, effect classification and safe response metadata. Failure categories distinguish invalid local input, unsupported capability/version, authentication/authorization refusal, not found, not cancelable, idempotency in flight/conflict, rate limiting, peer failure, invalid response, and transport uncertainty. These are responsibility-level results; raw provider exceptions are not the contract.

Use Java 21 `HttpClient` and existing Jackson in infrastructure; add no vendor SDK or runtime dependency. Keep the existing standalone payment adapter SDK's `java.base` dependency boundary unchanged. New responsibility values cannot contain Jackson, HTTP-client or JDBC types. Do not add public HTTP routes, database schema or workflow changes in this slice.

The adapter performs one application-level `sendAsync` invocation per call and has no application/background retry, sleep, journal or independent policy engine. Use HTTP/1.1 for this bounded tested surface. The JDK may retry a connection, a safe GET or a request it classifies as unprocessed by the peer. Those library attempts must retain the exact immutable origin, credential, method, path, body and idempotency identity inside the same total operation deadline. This is not a universal one-physical-request guarantee. Its descriptor advertises only this bounded lifecycle profile and the four supported operations. It advertises no financial execution owner, local freeze, artifact signature, mandate transport, provider method or customer action capability. It must fail existing native `Composition.Ports` capability checks rather than pretend to support `local-freeze` or `simulator-core` ownership.

## Response validation and evidence limits

Strictly decode bounded UTF-8 JSON, reject duplicate member names and trailing content, and cap body size, nesting and string lengths before projection. Reject incorrect successful status codes (for example create 200), non-JSON content, malformed session envelopes, missing required envelope fields, unknown lifecycle states, mismatching session identity on retrieve/update/cancel and a supplied mismatching protocol version. Validate the implemented projection and types of the required envelope fields: `id`, `status`, `currency`, `line_items`, `totals`, `fulfillment_options`, `messages`, `links` and `capabilities`. Currency must match this profile; a successful create/update must not silently change the requested currency. The session handle retains that currency for later calls.

This slice does not implement a general-purpose runtime validator for every nested pinned schema. Uninterpreted optional content remains protected opaque bytes, never trusted authority, executable instructions or model text. Unknown required capabilities must be rejected before later integration; no automatic schema download or handler selection occurs. Independent contract tests validate every authored successful request/response fixture against the complete hash-verified pinned JSON Schema, with remote reference resolution disabled. Runtime envelope checks plus these fixtures establish the named bounded profile; they do not establish arbitrary-peer full-schema conformance. Any later use of amounts, handlers, URLs, authentication metadata, buyer data or extensions requires reviewed validation before that content becomes actionable.

Return numeric status even when an error body is absent, HTML, malformed or oversized; do not parse such content as a success or lose the original status in a generic transport exception. Preserve only bounded, validated allowlisted metadata: `Request-Id`, `Idempotency-Key`, `Idempotent-Replayed`, and `Retry-After`. A header name alone does not make its value safe. Expose `Request-Id` or `Idempotency-Key` metadata only when the value exactly matches the trusted ID sent on this request; if no corresponding trusted ID was sent, omit the peer-supplied value. Different, duplicate/conflicting or malformed echoes remain protected or omitted and never enter diagnostics as text. A present conflicting idempotency echo is an invalid response, never permission to retry with another key; a conflicting request-ID echo cannot replace the trusted correlation identity. Record echo absence using fixed booleans/categories. `Idempotent-Replayed` accepts only the pinned literal `true` when present. Raw headers, `Set-Cookie`, authentication challenges, credentials and peer error `message`/`param` values are not copied into safe errors or logs. Peer error `code` is untrusted: only recognized fixed codes drive a local category; arbitrary text remains protected and is not exposed as an exception message.

## Authorization, transport and privacy

The application authorizes the tenant/principal's access to the configured merchant and session before dispatch, including before a local result replay. The adapter enforces immutable peer binding; credentials come from trusted adapter configuration/credential resolution, never a graph-supplied header. No new application API is exposed here, so this slice cannot claim end-user authorization evidence. Contract tests exercise refusal of mismatching scope/merchant/session bindings before any HTTP request. Actual application integration must supply independently reviewed object authorization.

Production transport configuration requires a trusted enrolled HTTPS origin and explicit credential binding. No redirects, automatic cross-origin authentication, URL credentials, query/fragment base URLs, uncontrolled proxy destinations, caller-selected hosts or dynamic schema URLs. Validate fixed base-origin/path policy and encode session IDs as one path segment; reject traversal, separators, control characters and ambiguous percent encoding. Never follow returned `continue_url`, links, handler schemas or authentication URLs. Ordinary HTTP is available only under an explicit loopback-test mode with a literal loopback address; test mode is not the default and accepts only synthetic credentials. Tests bind an ephemeral loopback port and make no external calls. Default launchers register no external peer.

Set connect and total operation deadlines, bound response reads and reject unsupported encodings. The total deadline covers connection, headers, the entire body, parsing and cancellation, including a peer that sends headers promptly and then stalls or trickles bytes. A header-only HTTP timeout is insufficient. Bound/cancel the body subscription and close its resources when the deadline or size limit wins; do not leave a blocked stream/background task alive after returning. Disable redirects explicitly rather than relying on a library default. The supported launch configuration must not enable `jdk.httpclient.enableAllMethodRetry`; reject a currently enabled value at construction, never mutate process-global properties, and do not claim this check observes an effective static JDK value initialized earlier in the process. The local pinned JDK's `MultiExchange` implementation caches retry settings, permits GET/HEAD retries, connection retries and a classified-unprocessed retry; the public client exposes no per-client universal retry disable switch. Evidence therefore counts observed peer requests and reports the permitted library-repeat limitation explicitly. An accepted POST followed by response loss must still produce uncertainty and one peer-observed request in the supported tested configuration; a dropped GET may produce two identical requests. A redirect, authentication failure or malformed response must not trigger a different host, credential, version, endpoint, operation or provider. Credential arrays/values and request/response body objects redact their string representation; logs/reports contain only fixed categories and safe correlation identifiers. Use synthetic fixtures only. Do not inspect local credentials, place secrets in test arguments, or send tokens to model context/checkpoints.

## Retry, uncertainty and persistence ownership

Checkout creation/update/cancel can change commerce state even without a charge. Timeout, reset, response loss, 5xx or an invalid response after a send therefore means the requested commerce effect is uncertain. It never means no effect. HTTP 404 on retrieve means the peer did not return that known session; it does not disprove an earlier create, complete or financial send. HTTP 405 cancel does not release financial exposure or imply a refund. A peer's `completed`, `canceled` or `expired` state remains a checkout lifecycle observation, not settlement or authoritative no-effect evidence.

The pinned protocol defines HTTP 400 `idempotency_key_required`, HTTP 409 `idempotency_in_flight` with required integer `Retry-After`, and HTTP 422 `idempotency_conflict`. Treat conflict as terminal for the immutable command, in-flight as wait/retry the same command only, and missing key as a client defect. Preserve other 4xx/5xx and HTTP 429 distinctly. Parse only bounded nonnegative seconds for the pinned 409 retry metadata; missing/malformed metadata is a protocol defect, not an immediate busy retry. The client returns advice; it never sleeps or resends itself. HTTP 401/403 cannot select a fallback credential automatically.

Callers own durable request/outcome persistence before this adapter can participate in recoverable application workflows. The required future record binds tenant/principal, enrolled merchant/configuration/credential identity (not secret), operation, exact path, exact body digest, idempotency key, session identity when known, original operation identity and response/uncertainty. Persist the request before dispatch, preserve the original key/body across crash/retry, and persist accepted outcome before acknowledging it. Local command, ACP HTTP and PSP financial keys are different scoped identities. A digest alone is insufficient to replay a command unless the original protected request bytes can be reconstructed exactly.

This standalone adapter supplies no durable ledger, financial outbox or process-restart recovery claim. Its contract requires callers to retain the immutable command. Tests can replay the same command against the peer, including a lost response after peer acceptance; that proves wire idempotency behavior, not durable platform recovery. If create loses its response before the session ID is known, do not invent a lookup-by-idempotency endpoint: only an agreed same-key replay/status mechanism can resolve it. The pinned contract gives no universal idempotency-retention guarantee; never assume a late replay remains safe after an unknown retention horizon.

No adapter network call runs under the JDBC run lock or transaction. A future platform integration requires a separately reviewed staged-command/dispatch/recheck protocol: persist intent and immutable transport command under a short transaction; send outside it; reopen a transaction to validate current revision/scope and store correlated outcome. A remote checkout update observed after approval must invalidate the prior exact signed checkout/authority binding before any financial admission. Moving a network call into `freeze`, `validate`, artifact `get`, or a new repository helper is not that protocol.

## Financial execution owner and signed-artifact gates

| Composition | Sole financial send owner | Required future admission/evidence |
| --- | --- | --- |
| This lifecycle slice | None; completion is absent | No grant consumption, budget reservation, charge, payment token or authority acceptance |
| External merchant completes and charges | External merchant's execution service | Bind one merchant completion operation to approved artifact/authority and retain unknown exposure; platform observes/reconciles that same operation and does not call a PSP independently |
| Merchant explicitly delegates to platform | Platform's already admitted payment operation | Merchant completion routes to that exact operation; one mapped owner/idempotency identity, no parallel merchant PSP send; verified backend payment evidence/receipts |
| Platform uses its own PSP adapter | Platform financial dispatch owner | Independently reviewed provider contract, atomic admission, immutable provider key, trusted authentication and reconciliation; external checkout cannot also charge |

Reject `/complete` before transport: there is no method or generic arbitrary-path escape hatch. Wrapping/decorating the lifecycle adapter cannot add completion permission by advertising an unknown capability. Never retry a payment via another execution path merely because a merchant/provider timed out.

The current ACP session response is not the AP2 merchant-signed `checkout_jwt`. Do not sign an external merchant payload with the local synthetic merchant key, enroll a key from the response, substitute a parsed/reserialized map for original signed bytes, or interpret TLS/API authentication as AP2 merchant authority. A future cooperative merchant needs an explicitly negotiated checkout-object and authenticated sidecar/extension profile supplying its original signed artifact and current frozen revision, enrolled merchant keys, exact signed-byte hash, AP2 roles/audiences/nonces, revocation ordering and receipt responsibilities. The [bridge blockers](../advanced/ap2-acp-bridge-design.md) remain active. Unsupported merchant signing, mandate delivery or handler capabilities fail closed rather than weakening the native profile.

## Provider sandbox feasibility, separately gated

The current `PaymentAdapter`, `ChargeOperation` and `CapabilityOffer` explicitly describe a synthetic adapter; the operation accepts only fixed simulator scenarios and the offer accepts only `simulator`/`synthetic-card`/`synthetic-reference` combinations. `sealNoEffect` requires an atomic future-send fence guaranteed by the local fake journal. A real provider's not-found result generally cannot establish that fence. Registering a renamed fake as a provider, coercing real statuses into those fixtures, or returning fabricated network IDs would be false integration evidence.

Before a named provider sandbox adapter is implemented, review a versioned responsibility contract/profile for token references resolved behind the adapter, explicit account/method/currency/region/channel support, authorization/capture distinctions, stable idempotency retention, query/event authority, authentication challenges and unknown-outcome recovery. Replace the fake-specific cancellation/fencing assumption only through an explicit negotiated capability and application policy; preserve existing fake behavior. Do not add a vendor-specific domain port. A provider implementation may independently use documented HTTP or wrap an official SDK behind that same reviewed responsibility contract, subject to dependency/license/security review.

No credentials or sandbox access have been established by this design. The next provider feasibility artifact must name one provider, exact pinned API/SDK contract, permitted test account/method, synthetic tokenization route, webhook signature/key requirements, idempotency/status retention, supported action flow and authoritative receipt fields. Read only primary provider documentation; do not infer access from ACP's open PSP strings. A local peer may test an independently authored provider transport against that documented wire, but only actual permitted sandbox exchanges can earn a sandbox-integration claim. No provider call is required or authorized for the current lifecycle slice.

## Acceptance tests and implementation gate

The implementation is one focused change: responsibility contract/values, JDK HTTP adapter, independently authored loopback peer tests, pinned-schema fixture probes and precise documentation. Use the existing build, Jackson and Python schema tooling. Retain upstream source bytes in ignored research cache; self-authored fixtures and exact lock identities are committed. Do not regenerate a broad client from examples or vendor an implementation.

Required evidence:

- Positive exact create/retrieve/update/cancel paths and methods; create 201 versus other success 200; no complete/provider endpoint exists. Empty cancel body is stable. Validate transmitted fixture bytes against the exact locked schema; retain negative obsolete `items`/`quantity` probes and the optional-version case.
- Peer rejects missing/wrong bearer credential and API version. Local scope/merchant/session mismatch makes zero HTTP requests. Verify caller-supplied POST keys and fixed request bodies survive a peer-accepted/lost-response retry; a changed payload with the same key produces the pinned 422 conflict. No application-level automatic retry occurs.
- Distinguish 409/valid `Retry-After`, malformed/missing retry metadata, 422, 401/403, 404, 405, 429, 5xx, unexpected 2xx, redirect, invalid JSON/UTF-8, duplicate JSON keys, trailing content, unsupported content encoding, body bounds, version/session mismatch and malformed success envelopes. Preserve original HTTP status and validated allowed metadata even when body parsing fails. Hostile `Request-Id`/`Idempotency-Key` echoes, including synthetic secret canaries, cannot replace trusted IDs or appear in results' safe metadata, string representations, errors or reports; absence and duplication follow the fixed rules above.
- A peer records POST acceptance then drops its response: result is uncertain and the same immutable command can be replayed once by the caller; no replacement key, endpoint, credential or financial path appears. Count requests at the peer to establish one POST observation before caller replay in the supported launch configuration. A separate dropped-GET test records permitted JDK repeats and checks that every observed request is immutable; it does not assert a universal single physical send. Reject currently enabled all-method retries without changing the setting. Separately test a peer that stalls before headers and a peer that flushes headers then stalls or trickles the body. Each hits the total bounded deadline and cancels/closes outstanding body work; observed library attempts remain bounded by the same deadline. No database lock is held because no payment-store wiring exists.
- Redirect to a second local server receives no request/credential. Reject untrusted origins/path injection and non-loopback HTTP configuration. Returned URL/schema fields are never fetched. Probe toString/errors/reports with synthetic credential, body and hostile echoed-header canaries; none is exposed. Sensitive headers and peer error text remain absent from safe diagnostics.
- A second independently implemented/decorated `CheckoutSessions` peer/client exercises the same contract values, supported-profile negotiation and failure semantics without naming ACP in application callers. Existing native composition/payment SDK tests remain unchanged and unsupported native registration fails explicitly.

Validation uses the relevant Java tests and independent pinned-schema probes, `pwsh -NoProfile -File scripts/Check-Docs.ps1`, `git diff --check`, and the documented full conformance run with isolated real PostgreSQL. Report exact source/run identity and actual test counts. Local peer success is reported as bounded ACP `2026-04-17` lifecycle wire evidence only. No existing certification gap is closed by assertion.

The Java loopback tests freshly generate `target/external-checkout-wire.json` from actual captured positive exchanges. Its format is `{"formatVersion":"external-checkout-wire-0.1","profile":"acp-2026-04-17-lifecycle-envelope-0.1","executionId":"standalone","cases":[{"operation":"create","method":"POST","path":"/checkout_sessions","status":201,"requestBody":{},"responseBody":{}}]}`. `executionId` is read from Java `System.getProperty("checkout.evidenceRun", "standalone")`; the conformance runner passes `-Dcheckout.evidenceRun=<stage executionId>` and invokes the independent verifier with `--execution-id` set to that same exact identity. Focused standalone tests use the literal `standalone`; default/standalone verifier mode accepts only that explicit value. The verifier rejects a missing, mismatching or stale execution identity rather than treating an earlier artifact as fresh. The displayed empty objects are shape placeholders, not valid fixture bodies. Include positive create/retrieve/update/cancel cases with the actual parsed synthetic request and response bodies; an absent request body is JSON null. Paths contain only synthetic session identifiers. Do not write headers, authentication, raw logs or canary/privacy-negative bodies into this artifact. Root-owned Python verification checks exact methods/paths/statuses and complete pinned schemas, rejects missing/extra operations and stale/missing captures, and joins the result to the existing fresh-run conformance stage. No manually retyped body substitutes for the captured bytes.

## Consequences and alternatives

This proves a genuine external HTTP boundary without prematurely making checkout transport into spend authority. The tradeoff is a deliberately standalone adapter: it cannot yet make the native purchasing workflow contact a merchant or execute a payment. Recovery persistence, signed checkout retrieval, merchant mandate acceptance, financial completion and provider sandbox execution remain explicit later gates.

Putting HTTP in existing `CheckoutProtocol.freeze` is smaller syntactically but violates transaction ownership and misrepresents merchant signing. Implementing complete immediately combines unresolved admission/sidecar/receipt/continuation semantics with a new network boundary. Wrapping a vendor SDK immediately still requires those contracts and access, and would not prove independent ACP wire behavior. A new payment-store facade does not resolve any of these issues. Those alternatives are rejected for this bounded slice.
