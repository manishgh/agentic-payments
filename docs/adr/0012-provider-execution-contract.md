# ADR 0012: Provider-neutral execution contract

Status: accepted for the bounded reference profile described below.

## Context and scope

The existing `io.agenticpayments.sdk.PaymentAdapter`, `CapabilityOffer`, `ChargeOperation` and `Money` deliberately implement a synthetic, closed local-fake profile. Its mandatory atomic absence seal is stronger than an arbitrary external provider can promise. Generic descriptors are metadata and cannot silently widen that executable contract. The [provider roadmap](../project/provider-adapter-evolution.md) describes the missing boundary.

Add a separately versioned, executable contract in `io.agenticpayments.sdk.execution.v1`, plus a reusable behavioral TCK in its `tck` subpackage and an explicit local-fake compatibility bridge in its `compat` subpackage. The version is `provider-execution-1`; protocol/profile revisions remain separate. Preserve existing SDK classes, stored JSON, simulator scenarios, old TCK behavior and the existing SDK classifier. All new SDK classes depend only on `java.base`; no new dependency, vendor SDK, network implementation, database port or financial dispatch change is required. The package is additive within the existing SDK classifier; package-release/POM separation remains an open release task.

This slice implements contract checks, independent synthetic fixtures, a delegating decorator and compatibility evidence. It does not implement Stripe/Adyen wire calls, claim a provider sandbox test, or connect the new interfaces to `JdbcPaymentStore`. Financial wiring requires a separate reviewed profile with durable admission/outbox/reconciliation evidence. The parallel durable checkout slice consumes neither these new interfaces nor a new provider execution path.

## Decision and responsibilities

Define interfaces by responsibility. A concrete adapter may implement several, but caller composition never depends on its concrete class or a vendor-named interface.

| Interface | Responsibility and boundary |
| --- | --- |
| `ExecutionPreparer` | Prepare the exact immutable operation under a selected profile. Explicitly declare whether this can create a nonfinancial external resource. Never authorize, confirm, capture or otherwise initiate a financial effect. |
| `FinancialSubmitter` | Submit the single financially admitted operation. It receives the immutable operation and optional prepared-resource reference; the surrounding caller owns admission. |
| `ExecutionReconciler` | Read evidence for that exact operation and original resource references. Lookup absence is inconclusive. It does not submit or create a replacement operation. |
| `ProviderEventVerifier` | Verify an opaque trusted-infrastructure event reference against its selected account/configuration and expected operation; emit a bound verified-event reference or a safe rejection. No raw request body or authentication header enters the contract. |
| `ProviderEventNormalizer` | Map an already verified, bound event reference to the selected profile's financial evidence. Verification and status interpretation remain independently replaceable responsibilities. |
| `NoEffectFencer` | Optional stronger extension: atomically prevent every delayed/future financial submission for the immutable operation if no financial acceptance won. Ordinary lookup/cancellation is insufficient. |

The interfaces accept immutable value objects and return explicit results. There is no default network retry, hidden provider failover, mutable current-account lookup, credential loading API or arbitrary exception message in the contract. A decorator must preserve identity, capabilities, effect certainty and evidence; it may add trusted metrics but cannot widen support or turn uncertainty into refusal.

### Immutable execution identity

`ExecutionOperation` contains:

- `ExecutionIdentity`: tenant ID, run ID, merchant ID, payment intent ID, attempt ID, operation ID and caller idempotency key, plus a SHA-256 request fingerprint. These are opaque synthetic-safe IDs, never email/address/card data.
- `ExecutionBinding`: provider ID, provider-account alias, region, immutable configuration reference and version, credential reference and version, and execution-owner ID. References are opaque identifiers resolved only by trusted infrastructure. A changed credential version is a changed binding even when the secret store alias is unchanged.
- `CapabilitySelection`: exact contract/profile versions, immutable offer digest, the exact selected supported combination, and the same binding. Selection is copied into the operation, rather than recomputed using current defaults on each delivery.
- `ExactMoney`: uppercase three-letter currency, explicitly bound minor-unit exponent and positive bounded integer minor units. Parsing accepts only canonical decimal integer text, never floating point, scientific notation, leading zeros or implicit currency exponent conversion. The selected offer supplies the permissible currency/exponent/range; the SDK does not infer provider support from an ISO-looking code.
- `OperationPurpose`: `AUTHORIZE` or `CHARGE` for this revision. Authorization does not mean capture. Separate later capture/refund operations require a separately reviewed contract/profile; they cannot reuse an authorization identity or enter through preparation.

The request fingerprint uses a pinned length-prefixed UTF-8 canonical encoding (`provider-execution-operation-1`) over all identity fields except the fingerprint itself, all binding fields, the complete capability selection, exact money and purpose. Sort every unordered set before encoding. Do not use `toString()`, locale formatting or delimiter concatenation with unescaped data. An operation constructor/factory recomputes and verifies the fingerprint. Duplicate key comparison uses the entire immutable operation as well as the fingerprint. Same durable caller key plus any changed identity/binding/money/selection/purpose is `IDENTITY_CONFLICT` before external activity; a digest alone is not a replacement for comparison.

The durable key namespace is exactly `(tenantId, merchantId, runId, callerIdempotencyKey)`. Provider, account, region, intent, attempt, operation ID and configuration are deliberately outside the namespace and are immutable bound values; changing them cannot evade conflict checking. A separately authenticated tenant/merchant/run may legitimately use the same caller-key text and obtains a different namespace. Adapter trusted configuration checks permitted tenant/merchant/run scope before journal access: changing scope on an invocation authenticated for the original scope is `INVALID_SELECTION`, not access to another namespace. TCK scope-mutation tests distinguish that rejection from legitimate scoped reuse.

Opaque IDs, versions and references have bounded ASCII token grammars; collections are bounded immutable defensive copies with no duplicate/ambiguous combinations. Constructor validation messages are fixed safe text and never interpolate rejected values. Raw provider payloads/secrets are unrepresentable. Reference-bearing values override diagnostics with fixed redacted text because even an opaque credential/account/action reference may reveal a sensitive alias. References remain restricted to trusted callers and are not public status/graph fields.

### Capability declaration and selection

`ExecutionOffer` declares contract version, profile version, provider ID, implementation revision and a nonempty set of `ExecutionCombination` values. Each combination explicitly binds method ID, credential-format ID, supported customer-action types, supported operation purposes, preparation effect (`EFFECT_FREE` or `RESOURCE_CREATING`), currency/exponent/amount limits and optional `ATOMIC_NO_EFFECT_FENCE`/`VERIFIED_EVENTS` capabilities. A currency can appear only once per combination. Provider support never implies support for a method, action or credential; combinations are complete tuples rather than a Cartesian product of independent catalogs.

`ExecutionRequirement` and `CapabilitySelector.select(offer, requirement, binding)` produce a concrete immutable `CapabilitySelection`. Trusted policy supplies the exact expected contract/profile/provider/implementation revision and required combination, including its required action set and preparation class. Unknown versions, capabilities, methods, credential formats, actions, unsupported money and ambiguity fail closed. Selection verifies provider/binding consistency and checks the configured account/region against the trusted requirement. An offer is an implementation declaration, not spending authority or permission to resolve an arbitrary caller-supplied account. Neither selection nor adapter invocation authorizes payment.

The operation must use the chosen tuple unchanged. The adapter validates selection digest, implementation/profile revision, configured account/region/configuration version and credential-reference version before external activity. A stale configured version does not silently migrate in-flight operations. An operator must retain the original configuration/credential resolver or reconcile through a separately reviewed recovery procedure. The offer digest is SHA-256 over a pinned canonical representation and covers every executable declaration, including preparation effects and fence support. Unknown advertised capabilities cannot acquire executable semantics merely by appearing in metadata.

### Preparation and financial submission

`PreparationResult` binds the exact operation and has `PreparationStatus` (`READY`, `ACTION_REQUIRED`, `UNKNOWN`, `REFUSED`), declared preparation effect, optional opaque prepared-resource reference and optional `TrustedActionDescriptor`. `RESOURCE_CREATING` means a nonfinancial resource may exist even when the response is lost. Repeating preparation must preserve the original binding/resource identity; the caller persists preparation identity before calling and retains uncertainty after a lost response. No preparation timeout authorizes creating a second resource or changing the financial operation. Preparation results never assert authorization/capture.

Preparation invariants are executable: an action descriptor is present if and only if status is `ACTION_REQUIRED`; an `EFFECT_FREE` result cannot carry an external-resource reference; resource-creating `READY` requires the original bound resource reference. `UNKNOWN` cannot claim readiness or invent a resource reference from absence; it may retain only an already known original reference. `REFUSED` is a preparation failure, not proof that no earlier financial submission exists. An unresolved preparation is not admissible for submit.

`FinancialSubmitter.submit(operation, optionalPreparedResource)` returns `ExecutionEvidence`. Its adapter must validate resource provenance and binding if supplied. Financial invocation is permitted only after a caller durably admits that exact operation; a Java type is not an admission proof. The caller persists request identity, original resource mapping, admission and outbox command atomically before invoking infrastructure. Preparation can require its own durable resource-creation command; it must not be hidden inside a transaction said to be effect-free.

Represent the invocation as immutable `SubmissionRequest(operation, optionalPreparedResource)`. Its pinned submission fingerprint binds the operation fingerprint and exact absent/present resource association. Before first financial activity, journal this association under the same durable execution key; every repeat must compare the entire request. Swapping a resource, changing absent to present or present to absent, or reusing another operation's resource is rejected before activity. The original operation fingerprint remains stable while preparation proceeds; resource association is a separately durable binding, never an untracked submit argument. A resource-creating combination requires a successfully resolved original prepared resource; an effect-free combination requires absence.

The adapter's durable idempotency responsibility is explicit: every accepted caller key is permanently bound to its immutable operation for the deployment's required audit/recovery horizon, independently of a provider's shorter idempotency retention. On restart, retries consult that binding. If it cannot establish that resubmission is safe, it reconciles or returns `UNKNOWN`; it does not resend merely because a PSP key may have expired or a lookup returned absent. The contract supplies the behavioral obligation, not an SDK in-memory map advertised as durable storage. Fixtures reconstruct their adapter over an independently inspected retained journal to test reconstruction behavior; this slice does not claim process-crash or storage-durability evidence.

### Evidence and financial meaning

`ExecutionEvidence` contains the operation, a safe evidence ID, optional opaque original provider-resource reference, evidence source (`SUBMIT`, `RECONCILIATION`, `VERIFIED_EVENT`, `FENCE`), observation time and `ExecutionState`:

| State | Meaning permitted by this contract |
| --- | --- |
| `UNKNOWN` | Financial acceptance/effect cannot be established. Preserve exposure and original identity. |
| `PENDING` | Provider accepted processing but financial completion is unresolved. Preserve exposure. |
| `ACTION_REQUIRED` | A trusted action is required to progress. Neither redirect nor UI completion establishes financial success. |
| `AUTHORIZED` | Exact amount authorized; not captured/settled. Only valid for a profile/purpose permitting authorization. |
| `CAPTURED` | Exact amount captured according to the selected profile. Does not independently assert bank settlement. |
| `DEFINITIVELY_REFUSED` | Trustworthy evidence establishes refusal with no financial acceptance for this operation. An arbitrary transport error is insufficient. |
| `NO_EFFECT_FENCED` | Optional atomic fence won before acceptance and prevents every delayed/future sender for this operation. |

All evidence must match exact identity, binding, money and purpose. `ACTION_REQUIRED` requires an action descriptor; other states cannot smuggle one. `AUTHORIZED` requires `AUTHORIZE`, and `CAPTURED` requires `CHARGE` in this bounded revision. Partial amounts, multi-capture, refunds and different financial mappings are unsupported, rather than silently coerced to full success.

Definitive refusal and a winning fence are terminal for financial submission of that immutable key: identical resubmission replays the original terminal fact and never starts acceptance. New financial facts that contradict a terminal fact remain reportable as conflicts rather than being discarded. A new user-approved attempt requires a separately admitted identity and cannot be initiated as transport retry.

An evidence ID deduplicates that exact payload; same ID with different payload is `EVIDENCE_CONFLICT`. Distinct facts may arrive out of order; observation time and transport order are not a global monotonic provider sequence. `UNKNOWN`/`PENDING` cannot erase established capture or authorization. A financial fact conflicting with definitive refusal/fence must surface a conflict and retain exposure for review. The SDK does not declare that every provider status model has a universal total ordering. Durable application applies evidence under its own reviewed atomic conflict rules; a TCK proves the adapter boundary only.

Evidence source is an explicit provenance assertion by a trusted port, not an authorization token. Caller-constructed `ExecutionEvidence` with source `VERIFIED_EVENT` cannot bypass event verification/normalization or be applied directly as payment truth. The caller accepts evidence only from its configured responsibility implementation and validated operation binding. Future financial wiring must enforce this provenance in its transaction boundary.

`ExecutionReconciler.reconcile(operation)` always returns evidence for that immutable operation. No resource/current lookup, 404, missing event, timeout, expired key or unverified merchant order state establishes definitive refusal/fence. It may report `UNKNOWN` with a fixed safe reason. Read-only reconciliation must never submit. Where an external resource cannot be bound to exact account, configuration and request, return uncertainty or reject its evidence instead of guessing.

### Verified events and trusted customer action

`EventVerificationRequest` contains the selected immutable operation and an opaque `eventEnvelopeRef`. Trusted infrastructure stores raw bytes/headers and performs secret resolution; these never enter workflow/model context. `ProviderEventVerifier` verifies authenticity, account/configuration scope, event identity and exact operation/resource/money binding. Its result is a `VerifiedEventReference` (opaque verified-event reference, event ID, exact operation fingerprint and binding digest) or a fixed safe verification error. `ProviderEventNormalizer` receives that verified reference and operation, validates trusted provenance through its injected trusted event resolver, and maps the pinned profile's event status to evidence. A caller-constructed Java value alone is not authenticity proof. Neither responsibility creates an authenticated fact from a parsed body alone. Duplicate verified events reproduce the same safe evidence, conflicting duplicates are refused, and unknown/unbound events do not mutate financial truth. A verifier implementation must document its exact signature/key/replay profile; a normalizer must document its financial mapping. The common SDK makes no vendor verification claim.

`TrustedActionDescriptor` contains only action type, opaque action reference, operation fingerprint, account/configuration binding digest and expiry. It contains no URL, HTML, client secret, OTP, credential, arbitrary map, provider payload or instructions to a model. Trusted UI/action infrastructure resolves the reference and validates expiry, current operation state, provenance and allowed origin before presentation. Completing an action feeds only a trusted signal into the original operation flow, never a new charge or a success assertion. `SYNTHETIC_CHALLENGE` is merely a compatibility profile action; external action formats require declared implementations and separate trusted UI evidence.

The SDK implements only descriptor validation and a pure binding/expiry check against an operation and caller-supplied trusted clock. It defines no UI presentation/completion port in this slice. `PE-ACTION` therefore tests descriptor structure, operation/account/config binding, expiry and the fact that descriptors are not financial evidence. Trusted completion, redirect provenance and actual UI behavior remain explicitly unevaluated composed obligations, rather than claimed by an adapter-only TCK.

### Optional no-effect fencing

The base interfaces have no `sealNoEffect`. Advertising `ATOMIC_NO_EFFECT_FENCE` requires a composed `NoEffectFencer` and a reviewed guarantee that the fence races atomically against all admitted/delayed submitters, survives restart, and prevents future financial acceptance. If acceptance already won, return the known evidence or `UNKNOWN`; do not issue a fence fact. Repeating a winning fence returns the original fact and submit must return that fact without sending. Ordinary cancellation or absence does not meet this guarantee. Providers lacking it pass the base contract while the fence extension is explicitly unsupported, with uncertainty retained.

### Safe failures

`ExecutionFailure` is a closed safe code plus effect certainty (`NOT_STARTED` or `MAY_HAVE_OCCURRED`), without arbitrary message, cause or provider payload fields. Codes include `UNSUPPORTED_CONTRACT`, `UNSUPPORTED_PROFILE`, `UNSUPPORTED_COMBINATION`, `INVALID_SELECTION`, `IDENTITY_CONFLICT`, `CONFIGURATION_UNAVAILABLE`, `PREPARATION_UNRESOLVED`, `TEMPORARILY_UNAVAILABLE`, `INVALID_EVENT`, `EVIDENCE_CONFLICT` and `CONTRACT_VIOLATION`. Invalid arguments use fixed safe validation text. Unknown provider/transport failures are sanitized at the adapter boundary.

`NOT_STARTED` means this invocation did not initiate activity; it never proves no prior/parallel invocation accepted the operation. A failure's retry advice cannot authorize a resend. Once external acceptance may have occurred, return `UNKNOWN` evidence or `MAY_HAVE_OCCURRED`; no thrown timeout is transformed into definitive refusal. Capability/identity/configuration validation is before activity. Raw exception causes are private infrastructure diagnostics, excluded from results/TCK reports; the TCK replaces unexpected runtime exceptions with a fixed incomplete-evidence result.

## Compatibility bridge

`compat.LocalFakeExecutionAdapter` implements the new responsibilities by wrapping an injected existing `PaymentAdapter`, plus an explicit immutable local profile/configuration and operation-to-scenario mapping provided by trusted test composition. Scenarios never enter the generic execution operation. It supports only existing local money limits, `CHARGE`, synthetic credential/method/action combinations and effect-free preparation. A changed local mapping for an accepted key is an identity conflict. It maps existing `SUCCEEDED` to `CAPTURED`, `PENDING` to `PENDING`, `NO_EFFECT` to `NO_EFFECT_FENCED` only when produced by the atomic local journal guarantee, and absent/unavailable lookup to `UNKNOWN`. The old fake's prepare challenge maps to an opaque synthetic action reference with deterministic binding/expiry supplied by trusted compatibility configuration. It cannot invent provider event authenticity: verified-event capability is unsupported unless an independent synthetic event verifier is explicitly supplied.

The bridge must preserve the old `OperationIdentity` mapping and old adapter key across restart. New fields cannot be discarded: trusted bridge configuration validates the permitted account/region/configuration/credential versions, and the compatibility journal binds the complete new operation before delegating. It does not pretend the existing `PaymentAdapter` alone durably stores all the new fields. Bridge journal behavior is exercised through the TCK with an independently inspected retained-memory fixture, explicitly reporting in-process reconstruction only; reference JDBC integration may supply a durable journal in a later financial-wiring slice. Existing core and simulator continue to call the original SDK directly.

The injected compatibility binding-journal responsibility atomically selects or retrieves the complete new operation, original legacy key/identity/scenario and exact submission-resource association under the execution namespace. Concurrent calls cannot choose different legacy mappings. Binding publication precedes delegation; a later failure preserves uncertainty and never fabricates a no-effect result. Synthetic retained-journal fixtures exercise reconstruction; the SDK supplies no in-memory journal advertised as production durability.

## Behavioral TCK and acceptance evidence

`tck.ExecutionTck` runs pinned mandatory versioned cases against `ExecutionTckFactory`/`ExecutionTckFixture`. Adapter scenarios are not part of the public operation. The TCK, not the adapter, chooses case IDs, mutations and fault instructions; fixtures provide test controls that implement those instructions. A missing control or unavailable observation is incomplete evidence, never an implicit skip/pass. The fixture supplies the composed interfaces, exact selected operation generator, independent inspection, explicit fault injection and restart. Cases exercise observable behavior and compare independently observed sends/resource creation/financial acceptances and binding journals. Adapter self-reported counts alone do not prove conformance. Every test fixture is isolated, synthetic and deterministic; no network account or credential is needed. Reports distinguish `IN_PROCESS_RECONSTRUCTION` from separately supplied `PROCESS_PERSISTENCE` evidence; the fixtures implemented here provide only the former. Real durable atomic journal/process-crash guarantees require separate integration evidence before financial wiring.

| Required case | Independent assertion |
| --- | --- |
| `PE-CAPABILITY` | Unsupported versions and each method/credential/action/purpose/currency combination reject before activity; two independent implementations and a forwarding decorator use the same interface unchanged. |
| `PE-IDENTITY` | Duplicate submit returns bound evidence with one acceptance; mutate amount/exponent/currency, each bound identity/config/credential/selection/purpose field, optional resource association and cross-operation resource reuse and observe safe rejection before another send. Unauthorized scope changes reject; a separately authenticated scope may legitimately reuse key text. |
| `PE-PREPARE` | Effect-free preparation creates nothing; declared resource creation is not financial; lost preparation response plus restart preserves original resource identity or uncertainty and never fabricates readiness. |
| `PE-UNCERTAINTY` | Accepted submit followed by response loss, restart, expired simulated provider deduplication and unavailable/absent lookup retains original key/resource and does not create another payment. |
| `PE-RECONCILE` | Read-only lookup never sends; missing lookup is `UNKNOWN`; pending/action/authorization/capture/refusal remain distinct and exactly bound. |
| `PE-EVENT` | Synthetic authenticated event verifies exact account/operation/money; forged, wrong-account, altered, conflicting duplicate and unbound events fail safely; exact duplicate is stable. Out-of-order event normalization emits each fact with its original meaning and never silently rewrites it as a stronger state. Atomic application monotonicity/conflict handling is an explicitly excluded composed obligation. |
| `PE-ACTION` | Descriptor has only allowed opaque fields; pure operation/account/config binding and expiry checks reject changed/expired descriptors, and an action descriptor cannot be passed as financial evidence. Actual trusted completion/UI provenance remains excluded. |
| `PE-SAFE-FAILURE` | Injected credential-like raw exception text/payload is absent from all returned failures and TCK evidence; `NOT_STARTED` does not certify operation-wide no effect. |
| `PE-FENCE` (conditional) | Unsupported fence stays explicitly unsupported; when declared, race/delayed-send/restart evidence proves acceptance-or-fence exclusivity and repeat submission after a winning fence never sends. |

Required base cases cannot be omitted to obtain a pass. Optional event/fence profiles are reported as unsupported when undeclared, and incomplete when declared without executable evidence. Reports name contract/profile/offer digest, suite revision, required/evaluated cases, adapter/fixture identities and exclusions; passing is adapter-only evidence, never whole-platform/provider/AP2/ACP/PCI certification. Broken fixtures/decorators that silently rebind accounts, overclaim fencing, retry uncertain sends or leak errors must make the suite fail. Two genuinely independent synthetic fixture implementations plus the compatibility bridge and forwarding decorator prevent tests from merely mirroring a reference adapter.

The standalone SDK remains dependent only on `java.base`. Provider-specific sandbox profiles and reviewed financial admission wiring are required before external execution.
