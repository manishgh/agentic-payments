# ADR 0007: Replaceable durable workflow runtimes

## Status

Proposed, 2026-11-07. Independent design review and an exact reviewed source identity are required before implementation. This decision authorizes no dependency installation, service deployment, paid service or external provider. Temporal, Cadence and Azure adapters are not implemented by this document.

## Context

[ADR 0006](0006-durable-ap2-admission.md) binds the independently implemented AP2 authority and embedded ACP checkout to the financial core. This decision covers a separate responsibility: durably coordinating that purchase across trusted approval, customer authentication, worker failure and uncertain payment outcomes. Payment truth and atomic admission remain in the Java/PostgreSQL core. A workflow history, completed activity or graph checkpoint cannot approve spending or prove payment success.

The current [Python workflow](../../workflows/payment_workflow.py) directly couples a LangGraph `StateGraph`, synchronous SQLite saver and HTTP command nodes. It has stable run/workflow command keys, safe status projection, manual interruption/resume and restart tests. The existing pins are LangGraph `1.2.20`, `langgraph-checkpoint-sqlite` `3.1.3`, `langgraph-checkpoint` `4.3.1` and CPython `3.12.14`. SQLite currently has one local driver and no durable distributed worker scheduler or automatic wake/timer service. Keep those capabilities explicit.

LangGraph persistence retains thread-scoped graph state; interrupts require the same thread identity and restart the interrupted node. Consequently, application side effects need independent idempotency and cannot treat resume data as consent. See the primary [persistence](https://docs.langchain.com/oss/python/langgraph/persistence) and [interrupt](https://docs.langchain.com/oss/python/langgraph/interrupts) documentation.

## Decision

### Separate decisions, scheduling and activities

Use responsibility-based contracts instead of embedding a particular scheduler in the payment workflow. One selected adapter owns scheduling/history for a workflow. LangGraph remains the shared decision implementation; runtime adapters translate its bounded decisions into their native durable scheduling primitives.

| Responsibility | Contract and boundary |
| --- | --- |
| Graph decision | Accept validated safe state, the last authoritative observation and an immutable decision-version identifier. Return one bounded typed decision and safe next graph state. No HTTP, clock reads, sleeping, signing, approval, customer actions or payment mutation. |
| Durable orchestration | Schedule the named activity, record its completion, retain safe state, wait for a wake notice or timer, and recover the same workflow. Replay code uses only runtime-provided deterministic scheduling/time primitives. It does not run the entire long-lived graph as one activity. |
| Activity implementation | Perform one bounded graph decision or one authenticated core HTTP command/read. Tokens live in the worker's injected client, outside arguments, results, history, heartbeat details and errors. Activities may run more than once. |
| Financial core | Own current checkout/authority, replay consumption, reservations, execution ownership, financial operation/outbox and verified outcome reconciliation. Workflow adapters cannot acquire these responsibilities by configuration. |

In the Temporal adapter, each LangGraph decision invocation is a short activity with a closed input/output contract. The deterministic Temporal workflow records the result and schedules the next named activity. It never imports or executes an arbitrary model/graph/network invocation during workflow replay. The SQLite adapter calls the same decision implementation and activity catalog while checkpointing its local progress. There are no two independent schedulers advancing one payment workflow.

The initial catalog contains `decide`, `create_intent`, `quote_intent`, `read_status` and `execute_existing_attempt`. Decisions are closed variants: create, quote, execute the existing approved attempt, wait for external change, and finish after an authoritative terminal observation. An unknown decision, activity name, profile or decision version fails closed. No activity dynamically names a URL, provider, Python function or credential. Future model decisions must remain a separately bounded activity with persisted validated output and an explicit policy/version; they receive no additional payment authority.

### Stable runtime port

The public Python-facing port contains ordinary immutable values and no Temporal, Cadence, Azure, LangGraph saver, database connection or SDK handle types. The precise implementation names can follow repository conventions; these responsibilities and semantic fields are fixed:

| Operation/value | Required behavior |
| --- | --- |
| `describe()` -> `RuntimeDescriptor` | Return adapter/version, contract version, supported capabilities, limits and history/privacy policy. Capabilities describe the configured deployment, not the vendor's maximum feature set. |
| `start(StartWorkflow)` -> `WorkflowRef` | Start one exact workflow identity with immutable profile, decision version, scenario and requirements. An identical duplicate returns its existing reference; changed semantic inputs conflict. Never replace a running/completed workflow implicitly. |
| `wake(WorkflowRef, WakeNotice)` | Validate the scoped caller and bounded event ID/reason. Request another authoritative read. It conveys no approved state, mandate, action decision or financial outcome. |
| `inspect(WorkflowRef)` -> `WorkflowObservation` | Return safe orchestration progress and its freshness/source. A payment status request separately reads the core; cached runtime progress is visibly not current payment truth. |
| `request_stop(WorkflowRef, StopRequest)` | Cooperatively stop new scheduling and return a safe receipt, preserving the payment references and recovery obligation. It cannot cancel a charge, revoke authority or release budget. |
| `resume(WorkflowRef, ResumeRequest)` | Resume a cooperatively paused, still-open workflow under the same reference, runtime binding, definition and command identities. Re-read authoritative core status before scheduling further work. A closed, failed or force-terminated history returns a fixed recovery-required result; this slice never silently starts a replacement execution. |
| `DecisionInput/DecisionResult` | Carry schema version, decision version, logical sequence, safe workflow state, validated observation and one typed next decision. Defensive validation occurs before history/checkpoint writes, including fake/test adapters. |
| `ActivityEnvelope` | Carry immutable activity kind/version, logical activity identity, safe exact request and core command identity where applicable. Transport attempt count is diagnostic and never enters the financial command identity. |

`WorkflowRef` includes the authenticated scope reference, simulator run UUID and caller-retained workflow UUID, plus the selected runtime binding/version. Runtime-generated execution/run IDs are opaque observation metadata. The runtime namespace/domain/task hub and worker queue are trusted deployment configuration. Supplying a workflow UUID does not grant access.

The runtime adapter uses a stable registration-store contract to retain the immutable scope, authenticated core-principal binding, run/workflow identity, selected runtime, canonical start-input fingerprint and definition/activity versions. Registration is atomically insert-if-absent; a different fingerprint or principal is a conflict. Concrete backends implement this same responsibility-based contract. Records/tombstones remain for the payment-reference lifetime, independently of scheduler history retention, and this slice exposes no deletion or identity-reuse operation. The local reference may use a durable SQLite registry with an explicit single registration-service capability; distributed registration requires a shared atomic implementation of that same port. Scheduler worker distribution does not imply distributed registry support.

Temporal starts explicitly reject workflow-ID reuse and do not replace a running execution. After atomically reserving registration, retry an uncertain start against the same Temporal workflow ID and fingerprint; confirm the existing execution's original registered input rather than blindly accepting any already-started result. An identical duplicate returns the original reference even after completion. If history has been purged, the retained registration prevents a fresh execution and reports history-unavailable/recovery-required when state cannot be inspected. Missing/unavailable registration infrastructure fails closed. Cross-runtime binding changes, principal changes and automatic recovery from closed/force-terminated histories are excluded until a separately reviewed fenced recovery protocol exists.

Persist an attempted-start marker before the first scheduler start RPC. For the bounded reference, an uncertain attempt is resolved by finding and confirming the same execution; an absent history after a recorded attempt yields recovery-required and never triggers a new start. NOT_FOUND cannot distinguish a never-created workflow from a purged one. Only a registration proven never attempted may initiate its first RPC. This conservative rule deliberately leaves a crash between the marker and RPC for operator recovery instead of risking identity reuse. Tests must cover accepted start with a lost response followed by simulated history purge.

Use a bounded provider-safe runtime ID such as `pay-v1-` plus SHA-256 over a canonical length-framed scope/run/workflow tuple. This is under Azure's documented 100-character instance limit and avoids restricted characters. Core create/quote/execute command keys preserve the existing algorithm and identities for existing workflows. New activity IDs derive from workflow identity, decision version, logical sequence and activity kind; activity retry attempts never change them. Scheduler restarts, continue-as-new, worker replacement and runtime execution IDs must not change a core command key, attempt, operation or adapter key. Azure documents instance identity and deterministic history replay in its [orchestration overview](https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-orchestrations).

Persist the decision version and activity contract version at start. Existing histories remain on compatible code until completed or explicitly migrated with replay tests. Unknown versions stop with a safe actionable failure. Never replay old activity results through newly changed decision semantics silently. Runtime selection is immutable for an active workflow; cross-runtime live migration needs a separately reviewed handoff/fencing protocol that prevents concurrent drivers. A wrapper may add telemetry or policy only while preserving identity, errors, provenance and effective capabilities.

An activity's exact request is bound to an immutable request-template/catalog version selected when the activity is created. History retains only safe selectors, versions and command identities; credential references and transport tokens remain in the trusted activity implementation. The worker materializes the same HTTP request from the retained versioned template on every retry. Missing templates, unsupported versions or a changed core principal fail closed rather than regenerating a request under an old key. A transport token may refresh only for the same bound principal and scope. Keep historical template implementations available while their workflows can resume.

### Wakes, timers, retries and cancellation

Trusted approval and synthetic authentication continue through their separate UI/core roles. A wake notice is only a hint that something may have changed. Every accepted notice, timer expiry or manual resume causes `read_status`; the workflow never copies asserted payment state from the notice. Notices may arrive before the wait, be duplicated, arrive out of order or be lost. The adapter must retain an accepted wake across worker restart and avoid the check-then-wait lost-wakeup race. Bounded event IDs support deduplication; duplicate reads are harmless. Automatic polling timers provide eventual progress when a notification is absent. No core-to-runtime notification transport is implied by this slice; explicit CLI wake plus polling is sufficient.

The Temporal workflow uses native conditions/signals and durable timers. Cadence and Azure implementations must map equivalent responsibilities through their own SDKs rather than emulate durability with process memory. [Temporal message passing](https://docs.temporal.io/develop/python/workflows/message-passing) and [Cadence workflows](https://cadenceworkflow.io/docs/concepts/workflows) document their distinct history and execution identity models. Matching the port does not imply their wire protocols or SDKs are interchangeable.

Activities have explicit bounded timeouts, bounded exponential retry policy and safe failures. Authentication/authorization errors, unknown contracts/capabilities and invalid inputs are nonretryable. Retriable transport failures reuse the exact activity request and core command key. Following a lost create/quote/execute response, retry the identical accepted request or read the existing resource; do not regenerate a command from later state under its old key. A version conflict can trigger a fresh status read, but changing an accepted command's payload/key is not automatic recovery. The core remains the last guard against duplicate financial effects. See [Temporal error handling](https://docs.temporal.io/develop/python/best-practices/error-handling) and [Cadence activities](https://cadenceworkflow.io/docs/concepts/activities/).

Read authoritative status immediately before executing an approved attempt and after its accepted response. Preserve a previously observed attempt/operation, reject a changed identity or regressed version, and treat historical idempotency receipts as receipts rather than latest state. `UNKNOWN` retains the same operation and held exposure; the workflow waits/reads while the core's existing runner reconciles it. Neither a scheduler timeout nor a retry creates another intent, switches providers or invokes an independent payment executor.

Timers measure orchestration waiting only; the core's transaction clock decides authority expiry and admission. A polling deadline may pause scheduling and require intervention but cannot infer financial no-effect. Cancellation is explicitly nonfinancial: stop new graph commands cooperatively, retain safe references and report that authoritative payment status/reconciliation remains required. Forced runtime termination is operational failure with the same recovery obligation. Stopping or canceling an activity cannot retract an HTTP request already accepted by the core. [Temporal cancellation](https://docs.temporal.io/develop/python/workflows/cancellation) supplies runtime cancellation mechanisms; it does not supply payment cancellation semantics.

Cooperative stop is a durable pause, not terminal cancellation. A stop receipt distinguishes `requested` from `applied`: an in-flight activity may finish before the workflow reaches a safe pause boundary, but no new financial command is scheduled after pause is applied. The Temporal workflow remains open in PAUSED state and accepts a same-reference resume signal; SQLite persists the equivalent pause marker. Wakes alone do not override an applied pause. Resume first reads the core and preserves any UNKNOWN operation and recovery obligation. An already terminal payment workflow remains terminal. Backend force-termination is not the public cooperative-stop implementation and cannot promise automatic resume.

### Capability negotiation and privacy

Define capabilities at the port boundary: `restart-resume`, `single-local-driver`, `distributed-workers`, `durable-wake`, `durable-timer`, `activity-retry`, `history-replay`, `cooperative-stop` and `versioned-decisions`. Requirements are supplied by trusted workflow configuration. Unknown required capabilities or missing deployment guarantees fail before workflow creation or any payment command. Do not downgrade to SQLite if a configured Temporal connection is unavailable.

The current SQLite reference can claim its tested manual restart/resume and single local driver only. Add further claims only when the adapter implements and tests them. The first Temporal adapter must prove durable wake/timer, retry, restart, replay and stop behavior against its pinned local deployment before advertising them. Cadence and Azure remain unregistered/unsupported until their adapters and reusable contract suites exist.

Runtime histories, SQLite rows, signals, queries, task payloads, search attributes, diagnostics and traces contain only an explicit validated allowlist: safe IDs, profile/contract/version, scenario, money, state, checkout revision/digest, exposure and reconciliation metadata. No bearer token, credential reference, OTP, private/public key material, raw ACP payload, compact JWT, mandate, signed receipt or arbitrary exception text enters these channels. Artifact-store references are unnecessary for orchestration and are excluded. Validate activity outputs before returning them to the scheduler, because rejection after recording is too late. Disable ambient tracing/exporters. This local reference makes no remote payload encryption or retention claim.

Validate start, wake, stop and resume inputs before calling an SDK serializer or registration write. Activity wrappers replace transport/parser exceptions with fixed bounded error codes and remove raw causes/details before the runtime can log or persist them. Template selectors are allowlisted safe values, never arbitrary request bodies. The local Temporal server and any enabled UI bind to loopback on a trusted development host; this slice provides no public runtime endpoint, production runtime authentication or remote tenancy boundary. Deployment transport/identity adapters require their own implementation evidence before external exposure.

## First concrete adapter and dependency decision

Implement one actual Temporal adapter alongside the bounded SQLite reference, after independent review. Use the existing Python process and ordinary bounded activities; do not add an LLM, provider connector, unofficial integration framework or an entire graph-as-activity shortcut. A local full Temporal development server with a persistent database file supports worker and server restart evidence without paid infrastructure. The official CLI supports native Windows binaries; `--db-filename` selects persistent state. See [CLI setup](https://docs.temporal.io/cli/setup-cli) and the [server command source](https://github.com/temporalio/documentation/blob/main/docs/cli/command-reference/server.mdx). This is development evidence, not a production high-availability deployment.

Select Temporal Python SDK `1.35.0` and CLI `1.10.0` as the implementation candidates observed on 2026-11-07. The tagged [SDK project metadata](https://github.com/temporalio/sdk-python/blob/1.35.0/pyproject.toml) supports Python >=3.10 and lists the base dependency constraints; use the Windows ABI3 wheel with Python 3.12. Install no optional agent, LangGraph, tracing or cloud extras. Keep LangGraph's existing pin. Record the resolved transitive versions, licenses and publisher hashes in the workflow lock/inventory before installation, and run dependency compatibility checks after it. Main-branch SDK documentation is not a substitute for the selected release.

## Acceptance and independent review

The independent reviewer must assess the exact ADR identity, capability contract, cancellation semantics, deterministic replay boundary and history privacy before implementation. Required implementation evidence is:

1. Reusable runtime contract tests cover duplicate start/input conflict, principal/scope isolation, uncertain start replay, retained registration after simulated history purge, prohibited identity reuse, unsupported capabilities, unknown decision version, wake-before-wait/duplicate wakes, bounded retries, timer recovery and cooperative stop/resume. SQLite's narrower claims are tested explicitly. Stop-requested versus stop-applied and safe refusal to resume a closed/force-terminated history have explicit observations.
2. The same LangGraph decision implementation runs through SQLite and the real Temporal adapter. Scheduler code performs no direct HTTP, random/time/model/graph execution during replay; short activities and fixed versions are visible in history.
3. The native purchase starts, pauses for trusted checkout approval, resumes from core status, pauses separately for customer authentication, then encounters response loss/UNKNOWN. Kill/restart workers and the persistent local server at controlled boundaries. Resume/reconcile the same attempt, operation and adapter key; PostgreSQL witnesses show one reservation and one simulator financial effect.
4. Crash after accepted create/quote/execute but before activity completion and prove exact-request replay. Spoofed wake payloads and a claimed approval/outcome cannot advance payment truth. Authority expiry/revocation remains enforced by the core.
5. Cancellation before and after admission never releases exposure, creates a replacement charge or reports payment cancellation/success. A stopped/failed runtime remains observable and recoverable against the original core references.
6. Scan checkpoint/history, wake/query/activity payloads, errors, logs and evidence with artifact/token/key/credential canaries. No raw upstream fields are persisted; safe projection and fixed failures are verified before scheduler serialization.
7. Replay retained Temporal histories under the same decision version, reject incompatible versions and prove the adapter does not silently switch runtimes when unavailable. Run dependency, existing graph/live/core, documentation and conformance gates without claiming external provider/AP2/ACP certification.

## Consequences and alternatives

This adds a real scheduling adapter and an explicit portability boundary while preserving the existing local workflow. It deliberately allows adapters to have different capabilities and operational requirements. Portability concerns responsibilities and safe contracts, not identical histories or a universal vendor SDK.

Running the existing long-lived graph inside one activity obscures activity boundaries, wake delivery and retry identity, so it is rejected. Executing arbitrary LangGraph/model code inside deterministic workflow replay is rejected. A new homemade distributed scheduler is unnecessary when Temporal supplies the chosen first runtime. Native LangGraph SQLite remains useful for one local driver, but it is not evidence of distributed durable timers or workers. Enabling every named runtime immediately would dilute the tested vertical slice; future adapters use the same contract and must supply their own implementation evidence.
