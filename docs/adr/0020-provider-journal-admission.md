# ADR 0020: Bind the synthetic provider journal to financial admission

Status: accepted for the bounded synthetic profile below.

## Decision and scope

Add an explicitly registered `local-provider-journal-admission-1` execution route, independent of the existing AP2/ACP authority profile. The legacy route remains the default. The new route supports effect-free preparation and the synthetic success, response-loss, delayed-success and definitive-no-effect scenarios. Customer challenges, resource-creating preparation, external events, authorization, refunds and real providers are excluded. Existing AP2/ACP approval, native verification, reservation and grant gates remain authoritative.

Every financial operation receives an immutable route marker in the same transaction that creates its operation and PREPARE work. V011 backfills existing operations with the explicit legacy marker. An opted-in operation additionally retains its complete core operation, checkout credential reference, provider execution operation, selection, account/configuration/credential versions, mapping policy and fixed observation times. Worker loading validates the complete retained registration before preparation, admission, reconciliation or evidence application. Missing or changed registration cannot fall back to the legacy adapter. Pure binding construction runs inside the core transaction; provider and journal calls never do.

The responsibility contract `ProviderExecutionRegistration` supplies pure binding and the exact retained values. `ProviderExecutionBindings` loads the complete retained association from an original operation identity, since legacy lookup carries neither amount nor scenario. Direct implementations, adapters and forwarding wrappers implement those same contracts. `JournaledPaymentAdapter` composes separately injected `ExecutionPreparer`, `FinancialSubmitter`, `ExecutionReconciler`, `NoEffectFencer` and `ProviderEvidenceVerifier`; its legacy SDK facade is only a bounded translation at the existing worker edge. Although fencing is optional in the general SDK, this bounded synthetic profile declares that extension and rejects an absent fencer before enrollment or provider activity. No vendor-named application port is introduced. `ProviderEvidenceVerifier` resolves exact retained evidence and checks quarantine; a DTO or source enum is not verification. Its `verify` method retains complete trusted-port input before exact provenance verification; `retained` resolves historical state evidence so late authentic pending observations remain verifiable after capture.

The public `JdbcPaymentStore.providerJournal` factory assembles the route's facade and uses that same facade as its fact verifier. A private constructor joins the assembled collaborators to the transaction owner. The public legacy constructor cannot accept a provider registration, preventing an accidental composition that records provider ownership but dispatches the original legacy peer key. Provider responsibilities remain independently replaceable through the factory.

The synthetic registration requires the approved checkout credential reference to equal the pinned provider credential reference (`fixture-credential-1`), and pins `synthetic-card` / `synthetic-reference`. There is no instrument alias substitution. The full core mapping includes the AP2-bound original request digest and exact money. `core-provider-map-1` copies core scope/intent/attempt/key, and forms the provider operation ID from the original UUID and immutable scenario. The existing bridge then applies its separate `local-fake-uuid-map-1` mapping to the dedicated synthetic peer namespace. The two identities are deliberately different; the original core operation is never executed through the peer directly, and existing legacy history is never adopted.

## Admission and recovery

Preparation may create the durable provider binding, but cannot claim financial ownership. DISPATCH rechecks authority, action and reservation policy and the retained execution binding, then atomically commits admission, DISPATCH completion and RECONCILE publication. Only the successfully returned committed ticket may call submit. Submit binds its complete request and takes the existing permanent journal claim before peer I/O. There is no transaction spanning the core, provider journal and peer.

A lost admission acknowledgement causes no send. A crash after admission but before journal claim leaves reconciliation of the original operation; it cannot recreate DISPATCH. A crash after claim never grants another sender. Lookup absence, timeout, expired provider idempotency or a changed configuration cannot justify another operation or send. The explicit genuine peer fence remains the only no-future-send resolution. UNKNOWN retains the reservation and cannot erase PENDING or terminal truth.

The legacy lookup facade maps UNKNOWN to its inconclusive `NOT_FOUND` no-fact result, which asserts neither actual absence nor no effect. This permits the existing explicitly requested `sealIfAbsent` path to invoke the configured genuine fencer. It never submits. Canonical projection ordinals are fixed and independent of this lookup result.

## Evidence projection and conflict

Every accepted port observation passes through the trusted journal's complete evidence retention and conflict matrix before projection, including direct, adapted and wrapped ports. The verifier requires exact retained evidence and checks quarantine. The synthetic projection gives PENDING ordinal 1 and CAPTURED / NO_EFFECT_FENCED ordinal 2. These are fixed semantic projection ordinals, never provider sequences or lookup counters. The canonical core event UUID uses length-prefixed full core identity, provider fingerprint and financial state. Repeated observations with changed source, timestamp or evidence ID produce the identical core Fact; full originals remain protected in the provider journal. UNKNOWN produces no financial Fact. Unsupported states fail closed.

PENDING after a fence and fence after acceptance are journal conflicts even where the old core sequence ordering would otherwise ignore an older projection. A dedicated safe `ProviderEvidenceConflict` propagates quarantine through a separate core transaction. `quarantineProvider` validates the exact retained operation and route, freezes the budget and retains deduplicated disputed exposure even for stale workers or terminal operations, then the original safe failure is returned. The provider journal retains the complete conflict receipt; core audit records the first creation of disputed exposure and does not fabricate a financial fact or duplicate an existing dispute. Existing final state is not rewritten as no effect. Unavailability is never interpreted as conflict or refusal.

The journal/core commit gap is explicit: settlement may commit before concurrently detected quarantine is observed by the core; subsequent explicit reconciliation must freeze and retain the dispute. The existing compatibility adapter may replay retained terminal evidence without querying later peer history. This route makes no general external event or continuous conflict-discovery claim.

## Implementation and verification

Application files define registration/binding, retained-evidence verification and the typed conflict signal. Infrastructure files implement the synthetic registration, facade/projection, JDBC retained-evidence verifier, explicit composition and V011 route persistence. `JdbcPaymentStore` owns atomic route enrollment, full load validation and quarantine writes. Worker policy only adds the typed quarantine path.

Tests cover direct/adapted/wrapped responsibilities; unchanged native rejection and no send; immutable credential/configuration/route restart rejection; exact durable mapping; one admission and permanent claim under contention; lost commit acknowledgement and child-process commit gaps; response-loss reconciliation; pending then capture without duplicate financial progress; stale authentic facts; pending/fence contradictions and post-terminal quarantine; safe failures and unchanged legacy operation behavior. Real PostgreSQL remains mandatory for durability evidence. No vendor or production certification is implied.
