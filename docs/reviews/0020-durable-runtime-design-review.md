## Architecture assessment

The proposed split is sound: one stable runtime port owns scheduling/recovery, a shared bounded LangGraph decision activity emits typed decisions, and narrow HTTP activities perform allowed core commands. Deterministic orchestration schedules these activities and records safe results; it does not replay graph/model/network work inline. The Java financial core remains the only owner of AP2 admission, reservations, operation identities and outcomes. A finished activity or workflow is not a payment receipt.

Temporal is one concrete adapter to the same responsibility contract that future Cadence or Azure adapters could implement. Capability negotiation must describe the configured deployment and be checked before payment commands. The SQLite adapter's manual single-driver restart guarantee is narrower; neither an interface name nor a successful Temporal test grants it distributed scheduling/timer behavior. Cadence/Azure implementations and cross-runtime migration remain deferred.

The reviewer checked the selected [Temporal 1.35.0 client source](https://github.com/temporalio/sdk-python/blob/1.35.0/temporalio/client/_client.py) and [project metadata](https://github.com/temporalio/sdk-python/blob/1.35.0/pyproject.toml), plus primary documentation on [workflow identities](https://docs.temporal.io/workflow-execution/workflowid-runid), [message passing](https://docs.temporal.io/develop/python/workflows/message-passing), [cancellation](https://docs.temporal.io/develop/python/workflows/cancellation) and [error handling](https://docs.temporal.io/develop/python/best-practices/error-handling). Activities may execute again after a lost completion. Temporal Run IDs change across execution chains, and closed-workflow duplicate rejection is limited by retained history. Those facts require application-level identity and lifecycle rules beyond SDK defaults.

The selected SDK metadata supports Python 3.12 and declares MIT licensing. This review does not verify downloaded distribution bytes or the complete resolved dependency inventory. The repository's pre-installation lock, hash and notice checks remain required; no optional agent/tracing integration or implicit test-server download is accepted.

## Findings and accepted dispositions

| ID | Finding | Required design disposition |
| --- | --- | --- |
| RT-001 | The initial port promises stopped/failed recovery but has no explicit resume operation, and does not define whether cooperative stop closes execution. A closed Temporal history cannot simply accept the same signals as an open workflow. | Add same-reference resume semantics and a precise lifecycle. Cooperative stop should retain a resumable paused workflow; distinguish request receipt from applied pause, and record outstanding activities. For forced termination/closed failure, fail closed and retain core reconciliation references; no implicit restart/replacement. Any later reset/handoff needs explicit fencing/version evidence. |
| RT-002 | Default Temporal start behavior does not implement semantic duplicate-start conflict or indefinite no-reuse. Once history expires, an old identity can appear unused. | Persist canonical semantic start fingerprint, selected runtime/versions and durable identity/tombstone for the supported workflow lifetime. Explicitly configure conflict/reuse policies, compare duplicate inputs and fail closed when registered history disappears. Persist attempted-start before the RPC. After uncertain start, absent history is not proof it never existed; fail closed unless a separately established minimum retention window proves retry safety. |
| RT-003 | Core idempotency is principal-scoped. Replacing a worker/session with a different principal can bypass the same apparent command key. History excludes credential references, yet a quote request needs the trusted credential fixture. | Bind workers to the original authenticated core principal and scope. Retain immutable request-template/catalog versions for each activity; safe selectors identify the exact request without putting credentials in history. Retries cannot reinterpret a pending request under new config or code. Missing historical templates/identity fail closed. |
| RT-004 | Sanitizing results after workflow serialization does not prevent history leakage. Default exception chains, wake bodies or arbitrary resume data can leak before normal output validation. | Validate all start/wake/stop/resume inputs before SDK calls; validate activity output before returning to the scheduler. Bound and sanitize error messages, causes, details, logs and heartbeat/search data. Only allowlisted safe values enter runtime persistence. |
| RT-005 | An unauthenticated local development scheduler is not a multi-tenant authentication boundary, and runtime cancellation does not retract accepted HTTP effects. | Bind development endpoints to loopback and treat backend/worker access as a trusted-host synthetic assumption. Adapter commands still enforce scope. Cooperative pause halts future scheduling; outstanding commands may commit and recovery must retain their exact identities and UNKNOWN exposure. |

All five findings are resolved in the final ADR. Same-reference `resume` and a nonterminal PAUSED lifecycle distinguish stop requested from applied; wakes cannot override pause. Durable registration binds the canonical start fingerprint, original core principal and selected runtime independently of retained history. Explicit reuse refusal and an attempted-start marker prevent a missing history from becoming a new payment. Immutable versioned request templates reconstruct credential-bearing requests inside the worker while retaining only safe selectors in history. Inputs are validated before SDK serialization and exception causes/details are sanitized before persistence. The development server/UI remain loopback services on a trusted host.

The final attempted-start rule is deliberately conservative: after a start RPC may have been attempted, recovery may only find and confirm that same execution. NOT_FOUND returns recovery-required. A crash after marking attempted but before the RPC can therefore require operator recovery despite creating no payment. This availability tradeoff is explicit and acceptable for the bounded reference; a future automated handoff/reset needs its own fenced design. The earlier phrase about retrying an uncertain start is constrained by this final rule and must not be implemented as a second start RPC on absent history.

## Bounded implementation acceptance

The following are required observations for source acceptance, not assertions that tests have passed:

1. One reusable contract suite exercises the SQLite subset and actual Temporal adapter: exact duplicate start returns the original logical workflow, changed input conflicts, cross-scope access fails, unsupported capabilities and versions fail before any core command, and a decorator preserves identity/capabilities. Reuse after completed/failed history and loss of registered history must not create a second payment.
2. The same versioned LangGraph decision implementation runs under both adapters. Temporal history shows bounded decision and core activities. Replay schedules only deterministic runtime primitives; HTTP, model/graph evaluation, wall-clock reads and randomness do not execute inline. Incompatible historical decision/activity/template versions fail safely; retained compatible code replays the recorded history.
3. Persist the complete safe activity envelope before first dispatch. Crash after each accepted create, quote and execute but before recording completion; retry identical semantic requests with identical command keys and principal. Database witnesses show one intent, current checkout, attempt, reservation and operation. Changed worker configuration cannot silently alter a pending request.
4. Test wake-before-wait, wake during an activity, duplicate/out-of-order wake, worker-down delivery, durable timer recovery and absent notification polling. Wakes only trigger authoritative reads. A malicious approval/action/outcome assertion is rejected before history serialization and cannot mutate financial truth.
5. Prove the full synthetic AP2 purchase: checkout, trusted UI approval, separate authentication pause, controlled worker/server restart, lost response/UNKNOWN, resumed authoritative reads and same-operation reconciliation. Use the persistent local server and fresh worker processes, with deterministic barriers rather than arbitrary sleeps. One simulator effect and one eventual budget settlement must be witnessed in PostgreSQL.
6. Pause before an activity starts and while an HTTP command may already have been accepted. Report pause requested versus applied accurately, retain the in-flight identity, and resume the same logical workflow. Pausing after admission cannot release UNKNOWN exposure or imply payment cancellation. Forced termination retains visible recovery obligations and cannot be bypassed by duplicate `start`.
7. Include token, artifact, key, credential and exception canaries in rejected inputs, fake client output and chained failures. Inspect raw scheduler histories, SQLite rows, activity/signal/query payloads, diagnostics and safe reports. Validation must occur before persistence, not merely when presenting a result. Token refresh stays outside persisted values and preserves principal scope.
8. Verify installed bytes against publisher hashes before use, preserve dependency notices, pin transitive versions and run dependency compatibility checks. Disable implicit test-server download. Run the real persistent-server/worker restart checks in addition to any replay/time-skipping unit tests, then the existing graph/core/UI and aggregate gates. Record only supported deployment capabilities.

The selected workflow deliberately cannot approve checkout, complete customer authentication, submit raw AP2 artifacts, switch payment provider, create a replacement payment or settle exposure. `request_stop` and runtime errors must preserve that boundary. Historical command receipts require a new authoritative status read before subsequent financial decisions.
