# Native AP2 direct authorization requirements

Status: requirements for a bounded independent Java implementation, 2026-11-07. This is a project profile of AP2 v0.2, with offline synthetic identities and explicit trust configuration. It is not an AP2 certification, Google SDK implementation, live payment connector, or evidence of interoperability with another implementation.

AUTH references RFC 9901 SD-JWT, RFC 7800 confirmation keys, OpenID4VP and an individual Delegate SD-JWT draft. This first slice deliberately does not implement the user-credential, OpenID4VP, holder-key-binding or delegation-chain paths. Its positive path must still be an SD-JWT representation of directly approved closed content, with an explicitly trusted Agent Provider issuer; a merchant signature or unsigned JSON content alone cannot establish user authority.

## Role and requirement matrix

The requirement IDs below identify this project's evidence obligations, not upstream certification identifiers. Tests distinguish protocol obligations from the narrower project choices. A signed fixture proves the configured synthetic issuer's assertion; it cannot prove that a human actually used a consent UI.

## Independent fixture design and acceptance evidence

Use Python's already reviewed `cryptography` dependency to create transient EC keys and ES256 signatures independently of the Java verifier. Do not import the production Java implementation, run the Google SDK, or copy upstream implementation logic. Retain only public JWKs, synthetic public artifacts, trusted expected inputs, manifest expectations and source/profile identifiers. Private keys exist only in the fixture generator's memory and are never serialized. Fixture bundles may include signed synthetic mandates, but no real credential, card data or personal identity.

The fixture plan is a positive checkout/payment pair and typed success/error receipts, followed by individually mutated trust, syntax, authority, binding and reference cases. Construct content-mismatch cases with valid independent signatures to ensure semantic checks run beyond signature verification. Include exact-byte changes and re-signing to distinguish hash-domain correctness from JSON equivalence. Static expected outcomes are author-written from the requirements, never generated by invoking the Java verifier. Primitive ES256 representation also has the existing public RFC 7515 A.3 vector; that primitive evidence does not substitute for a complete native mandate fixture.

Java tests consume generated public bundles and assert acceptance or the documented error category, plus safe-output boundaries. Generation is an explicit offline setup/test action, without network calls. A reproducible test concerns assertion outcomes and recomputable exact-byte hashes; randomized public fixture signatures need not be byte-identical across generation runs. The integration owner records actual Java build/test results and broader conformance observations. Until those results exist, this matrix is planned coverage.

## Profile choices and unresolved upstream ambiguities

The chosen authority envelope requires protected `typ=dc+sd-jwt`, outer `vct=https://agentic-payments.example/profiles/ap2-direct/1`, explicit issuer/time/audience/nonce/identifier claims, `_sd_alg=sha-256` and exactly one inline closed content object in `delegate_payload`. Wire serialization is `issuerJWT~`. Public-key metadata and Java APIs are frozen in the reviewed design before implementation. This is a narrowed representation based on AUTH's provider model; it is not an assertion that all AP2 peers choose that envelope. No nonempty selective disclosure or holder binding is silently ignored.

The profile uses the compact checkout JWS string directly in `checkout_jwt`, and hashes its ASCII bytes. The schema description says base64url-encoded serialized JWT while prose/examples carry the compact value. This is an explicit profile resolution requiring peer agreement. Likewise, AUTH's generic receipts use lowercase `result`, while AP2-specific schemas use capitalized `status`; this slice requires both fields with consistent values, retaining the AP2-specific required fields. The receipt-status schema's filename/`$id` mismatch is existing source evidence, not a reason for remote resolution or patched normative bytes. Real networkless success remains unsupported because the pinned Payment Receipt success schema requires both confirmation IDs.

## Deferred and unsupported paths

| Path | Required future work |
| --- | --- |
| User Credential issuer/holder model | Pin issuance/presentation/delegate revisions; verify issuer credentials, disclosures, holder keys, nonce/audience and transaction-data binding. |
| Autonomous/open mandates | Full chain verification, unchanged inherited claims, every known constraint, `cnf` proof of possession, selective disclosure and durable receipt-controlled reuse/budget accounting. Unknown constraints must continue to fail closed. |
| General SD-JWT privacy/KB | Recursive disclosure processing, salts/digests/decoys, nested arrays, holder binding and algorithm handling with independent vectors. Zero-disclosure direct content does not implement those features. |
| Agent-to-agent delegation | Separately specified chain semantics; AP2 v0.2 itself places this outside scope. |
| Production trusted surface/trust discovery | Human identity and consent evidence, key custody, enrollment, rotation/revocation discovery, authenticated channels and operational audit. Synthetic trust fixtures establish none of these. |
| Credential Provider and MPP execution | Instrument ownership, scoped token issuance/release, actual provider authentication, sandbox connector, one financial execution owner, idempotency and reconciliation. |
| ACP bridge | Negotiated exact checkout-object transport, authenticated sidecar, current revision/receipt acceptance and resolutions of recorded upstream blockers. Existing offline lab stays separate. |
| Durable admission/replay prevention | Bind verified authority to tenant/intent/attempt/operation with atomic replay consumption before any core dispatch. The process-local replay guard supplies no durable financial replay protection. |
| External interoperability/conformance | Exchange and verify artifacts with a named independent peer at the exact version/profile, then record evidence and remaining gaps. Independently generated Python vectors are cross-language tests, not Google interoperability. |
| Dispute operations and retention | Protected evidence persistence, authorization, retrieval, retention and legal/process semantics. Hash/reference validation alone supplies no operational dispute service. |

No unsupported path grants partial authority. A future extension needs requirements, reviewed design, independent adversarial evidence and explicit integration acceptance before enabling any payment capability.
