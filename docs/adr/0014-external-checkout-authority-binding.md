# ADR 0014: Bind external checkout observations to synthetic AP2 authority

## Status

Accepted for the bounded reference profile described below. See the platform guides and executable tests for current implementation limits.

## Context

The durable commerce lifecycle retains exact external ACP response bytes, scoped request identity and uncertainty. Native financial admission separately binds independently verified AP2 mandates to a generated checkout, grant, replay identities and reservation. A lifecycle `ready_for_payment` response supplies neither spending authority nor a merchant signature. The current native checkout validator deliberately accepts only its generated fixture tree; substituting an external payload there would weaken an existing guarantee.

The next executable slice joins these boundaries while retaining their separate responsibilities. It uses a controlled synthetic external merchant, locally attests an exact observation, obtains trusted human approval and executes only the existing synthetic payment adapter. It never invokes remote checkout completion or the provider-execution SDK/journal. Existing native and commerce profiles retain their behavior.

## Decision and explicit profile

Add `local-external-ap2-acp-single-tender-0.1`. It uses the existing independently authored `ap2-v0.2-direct-tap-synthetic-0.1` authority engine and pinned ACP `2026-04-17` response subset. Its execution owner remains `simulator-core`. Only `merchant-demo`, USD/EUR, one full-total synthetic-card tender and `fixture-credential-1` are supported.

The checkout JWS is a **local synthetic attestation of retained HTTP bytes**, made by an explicitly enrolled fixture signer. It is not a signature supplied by the external merchant and proves no production merchant delegation. The reference key/profile registration must identify this provenance; AP2's existing merchant-checkout verification role describes the synthetic role fulfilled by that trusted fixture. HTTP metadata, issuer strings in payloads and successful parsing never enroll keys or authorize issuance. Enrollment remains trusted infrastructure; approval remains required.

External financial binding is disabled by default and needs separate explicit trusted registration, in addition to the existing commerce origin opt-in. Registration binds the exact tenant/run/source principal/merchant/configuration identity, configuration and credential versions, transport/encoding profile, fingerprint, supported synthetic terms policy, attestation policy and clock profile. A request cannot select a URL, key, configuration replacement or clock policy. A replacement may implement, adapt or wrap the same responsibility interfaces. No vendor-specific interface is introduced.

The profile does not assert that remote state is immutable. Its permanent local seal prevents this application's future commands, while the controlled synthetic peer assumption and bounded observation lifetime limit the claim. Independent merchant mutation, externally hosted commerce, live instruments, remote completion, generic ACP handler negotiation and production freshness guarantees need another reviewed profile.

## Responsibility and API contracts

### Application and transaction owner

Add `PaymentService.ExternalQuoteCommand(expectedVersion, purchaseId, expectedPurchaseRevision, responseReference, tenders)` and `quoteExternal(session, intentId, localKey, command)` to the existing service/store boundary. `PaymentStore` supplies a default unsupported implementation and explicitly advertises `atomic-external-checkout-binding-0.1` in addition to `atomic-replay-grant-reservation-0.1` when implemented. The new capability promises atomic source validation, permanent seal and quote publication under the same ordering used by lifecycle mutations/configuration changes and financial admission. Generic CRUD or two independent transactions cannot advertise it.

The HTTP route is `POST /internal/v0.1/intents/{intentId}/quote-external`. It requires `intent:write`, normal current merchant authorization and the existing local `Idempotency-Key`. The exact JSON members are `expectedVersion`, `purchaseId`, `expectedPurchaseRevision`, `responseReference`, `tenders`; tender retains existing provider/method/credentialReference shape. UUIDs must be canonical, revisions positive, one tender required, duplicate/unknown members and wrong scalar types rejected. There are no caller amounts, signed artifacts, raw responses, source-principal selectors or signer fields. Only an external-profile DRAFT intent can accept this command. Existing `quote` rejects external-profile intents; external quote rejects other profiles. No rebinding/requote is supported.

Return the existing safe quote fields: intent/state/version, financial checkoutRevision/digest, exact money and quoteExpiresAt. The existing checkout view and trusted approval route then work unchanged. Approval always binds the reviewed financial digest/revision, not a lifecycle status. The safe view may identify the external profile and local-synthetic-attestation provenance, but exposes no remote session identifier, raw body, configuration credential, private key or mandate.

New calls authorize current access before replay lookup. An identical accepted retry returns its original result without signing, recapturing freshness or creating another binding; changed input conflicts. Current expiry/configuration does not rewrite an accepted historical decision. This does not waive checks for a new approval, execute or dispatch. Source lookup during quote is scoped to the authenticated lifecycle principal. The binding records that source principal immutably: later approval by `customer-demo` and worker execution must resolve the original `agent-demo` source through the trusted intent binding, not through the later caller's principal and not through an untrusted request field.

### Existing protocol ports, additive methods

Keep one checkout-protocol responsibility. Extend `Composition.CheckoutProtocol` with fail-closed default methods:

- `inspectObserved(ObservedCheckout observation, Instant now) -> ObservedTerms`;
- `freezeObserved(ObservedCheckoutRequest request) -> FrozenCheckout`.

`ObservedCheckout` is a protected immutable record supplied only after transactional source loading. It carries scoped purchase/command/response identities, source revision, exact configuration identity, trusted observation time, original `Document` projection and cloned exact response bytes. Its string representation is redacted. `ObservedTerms` carries remote session, protocol/handler identity, currency, exact minor amount and remote expiry; it cannot carry enrollment or grant authority. `ObservedCheckoutRequest` combines the retained observation, derived `CheckoutFacts` and enrolled signing identity. Exact Java record organization may use nested records, but these semantic inputs and outputs are required.

The external checkout implementation parses the closed response subset, freezes exactly its original byte sequence and validates its JWS and bounded terms. Native `freeze` and its full generated-tree validation stay unchanged. External adapters must not implement native generated-checkout support accidentally. Capability negotiation requires `exact-observed-checkout` and `local-synthetic-attestation` for this path; default methods reject. Unsupported local-freeze operations on the external adapter reject.

`Composition.Ports.requireSupported(profile)` selects requirements for that explicit profile; the existing no-argument overload retains native behavior. Existing issuer/verifier, artifact, provisioning and key-resolution ports explicitly declare external support only where their behavior satisfies it. No inferred fallback from native registration is allowed. `PaymentServices.local` gains explicit external registration/composition injection while retaining existing constructors and default-disabled behavior. A profile-indexed registration or equivalent distinct native/external Ports inputs is acceptable; caller behavior must not depend on the concrete adapter class. Select the checkout implementation and profile-configured coordinator from the trusted persisted intent profile, never from response/session heuristics. Preserve the existing StoredCheckout JSON shape; no new discriminator in historical artifact records is required.

The application coordinator owns observation-to-facts policy and cross-checks adapter output: exact raw payload equality, raw digest, source/session/protocol/handler identity, amount/currency, effective deadline and the signed JWS payload all agree. It stages/reloads immutable artifacts and uses existing independent AP2 verification. A successful issuer or protocol method is not itself proof of authority. JDBC owns transactions, trust snapshots, current source/configuration checks and financial records. No JDBC type enters domain/application protocol records.

The financial `PaymentStore` remains the transaction contract; do not add a second independently committed observation repository to perform sealing. JDBC may share infrastructure row-mapping helpers with lifecycle storage. The reference lifecycle stage/claim adapters must enforce the same persistent seal. Add default `CheckoutLifecycleTransactions.bindingCapabilities()` returning an empty set; the JDBC implementation advertises `atomic-external-checkout-binding-0.1`. Registration fails closed if lifecycle storage cannot advertise/preserve this guarantee or does not share the same authoritative lock/transaction domain. Direct adapter calls must enforce it as well as application policy.

## Supported response and exact bytes

Financial-ready responses use the same closed synthetic ACP shape already generated by `NativeComposition`, with these deliberate differences: `id` is the actual retained remote `cs_...` session, and the sole item id is `demo-item` or `demo-item-alt`. The item name is `Synthetic item`, line id `synthetic-line-1`, quantity integer 1. Unit amount, line total and root total are the same positive exact integral minor amount, at most 999999999999. The independent peer supplies 1250 for demo-item and 1750 for demo-item-alt; the financial core derives money from the bytes, never a native cart default. Currency is lowercase `usd` or `eur` and becomes uppercase only in the normalized financial facts.

Require `status=ready_for_payment`, exact protocol version, exactly one root/line `total` with display_text `Total`, empty fulfillment_options/messages/links and the complete existing synthetic handler object: id `synthetic-handler-1`, name `invalid.example.synthetic.card`, ACP version, fixed `.invalid` spec/schema links, `requires_delegate_payment=false`, `requires_pci_compliance=false`, psp `synthetic-psp`, one fixed instrument schema and config merchant_id `merchant-demo` / environment `offline-only`. Require an explicit RFC3339 UTC expiry. No additional root/nested fields, metadata, handlers, actions, instruments, quantities, totals, numeric strings/fractions or nonfinite/overflow values are supported. Existing lifecycle-only responses with empty totals remain valid commerce observations but are ineligible for financial binding.

Use strict UTF-8 and duplicate-member rejecting bounded JSON parsing. The implementation must enforce the entire closed subset, including all nested types and exact money arithmetic, independently of the transport's projection. Independent validation against the pinned upstream schema proves the synthetic fixture is within that schema; this introduces no new runtime schema library. Unknown fields/capabilities fail explicitly. Parse for validation only: never canonicalize, reorder, normalize whitespace or regenerate signed input. Accepted harmless whitespace/order variations remain distinct byte identities.

Compute artifact SHA-256 over raw response bytes. Separately recompute the existing lifecycle digest `SHA256(base64(rawBytes))` using its existing encoding. These identities are intentionally different. Recompute the retained request digest using the existing lifecycle prepared-request encoding. An opaque response UUID is a selector, not a proof. The exact response equals the stored ACP artifact bytes and the decoded checkout-JWS payload byte for byte. Mandates bind that exact checkout JWS/hash as before.

## Clock, freshness and current trust

The bounded timestamp format is a four-digit-year RFC3339 UTC `Z` value with hours 00–23, minutes/seconds 00–59 and optional one to nine fractional digits. Invalid calendar dates and lexical forms, including leap-second/midnight normalization, fail as `AUTHORITY_BINDING_INVALID`. Valid timestamps with nonzero precision below a microsecond fail as `UNSUPPORTED_CAPABILITY` before quote publication or sealing. PostgreSQL stores microsecond precision; accepted source bytes are never rounded or rewritten.

The new migration records non-null `observed_at` from the locked run's trusted virtual clock only for a current OK response promoted to the purchase projection; all other retained outcomes leave it null; it must never be supplied by HTTP Date, peer metadata or quote input. Historical outcomes lacking this field are ineligible. A valid later observation may supply time only when no uncertainty barrier exists. Recording a late/stale outcome does not refresh eligibility.

This synthetic profile explicitly uses the same reference virtual-clock domain for peer `expires_at`, trusted observation time and financial authority. The demo defaults to the existing run origin `2026-11-06T10:00:00Z` and peer expiry `2026-11-06T10:15:00Z`; independently injected test fixtures declare their common clock/expiry. It does not interpret real merchant wall-clock expiry against a frozen simulator clock. A future wall-clock profile requires separately reviewed clock/freshness policy.

Reject future observations (`now < observed_at`) and expired evidence (`now >= observed_at + 300 seconds` or `now >= remoteExpiresAt`). Effective quote deadline is `min(observed_at + 300 seconds, remoteExpiresAt)`, never quote-time-plus-lifetime. Approval's mandate deadline additionally intersects trusted approval time plus 300 seconds and grant expiry. Key validity/revocation is checked independently at every applicable current-trust gate, preserving the native policy; this slice does not claim an additional stored deadline capped to every key expiry. Exact boundary equality is expired. Replaying or rereading cannot extend any deadline.

Each new quote, approval, execution and pre-admission prepare/dispatch gate rechecks the original source/configuration/trust and deadline under the run lock. If configuration changed/unregistered or required trusted policy is absent, reject before new financial admission; do not silently use another credential/version. Source and configuration verification is local database/trusted registration work, not a merchant retrieve. The bounded reference uses local fixture signing/provisioning and existing immutable artifact retention; merchant HTTP never occurs inside financial transactions. Trusted external-profile registration must assert `bounded-local-callbacks-0.1` for every callback invoked under the run lock: checkout protocol, authority issuer/verifier, artifact storage, provisioning, signature primitive and key resolver. This means bounded local computation and the existing reference database/artifact retention only, with no outbound remote service calls. Absence of this trusted registration assertion fails closed before binding; neither request input nor an untrusted callback self-assertion can enable it. Remote signing/artifact implementations requiring externally blocking coordination are not automatically enabled by interface compatibility and require a reviewed profile/transaction strategy.

## Atomic state and persistence

Add `V010__external_checkout_authority_binding.sql`; prior migrations/checksums remain untouched. Add nullable `observed_at` to outcomes, with no fabricated backfill, and a durable binding table scoped by tenant/run/source principal/purchase. The binding stores intent id, source command/response/revision/configuration identity, observed time, raw digest, effective expiry and attestation provenance. Use scoped foreign keys to purchase/outcome and intent, unique purchase ownership and unique intent binding. Native financial snapshot/artifact/authority tables retain their formats. The profile allowlist constraint must admit the new explicit profile. Migrator registration and upgrade tests accompany the additive migration; no destructive down migration or automatic unseal exists.

The existing `simulation_runs(tenant_id,run_id) FOR UPDATE` orders lifecycle stage/claim/outcome/recovery, configuration enrollment, quote binding and financial admission. Quote executes these steps in that transaction:

1. Authorize scope and current merchant access; replay accepted identical commands first.
2. Check intent profile/state/version and read the exact caller-owned purchase/current command/current response under the lock. Reject a permanent mutation barrier and any STAGED/CLAIMED command, including a GET. Require RECORDED / OK / OBSERVED / successful 2xx, non-stale retained outcome, known matching session and exact current configuration. Check selected purchase revision, command identity, prepared request, source binding, request digest and retained outcome claim/correlation linkage. Parsed raw session/currency/status/version must equal retained Document and current projection; remote status must be ready_for_payment. Recompute both document digests.
3. Check trusted registration and non-null observation time; inspect bounded terms and calculate deadline. Ensure the purchase is unbound and this intent has no external binding. A purchase already bound to another intent is a binding conflict, not an authority-replay error.
4. Provision trusted local attestation enrollment, sign exact bytes, retain/reload artifacts and validate with current trust. Insert financial snapshot/native artifact references plus permanent source binding/seal, update intent to QUOTED and store accepted command result atomically. Artifact-store writes may leave unreferenced immutable bytes on SQL rollback; they cannot confer admission.

After commit, **all new lifecycle stage operations**, including RETRIEVE, reject for the sealed purchase. Stage and claim enforce this in the transaction adapter. Existing status reads and identical historical command retries remain available and cannot send again. No active command may coexist with a new seal. A race between quote and stage has one lock-ordered winner; the loser rejects. A recovered or stale mutation permanently blocks binding even if later GET reports ready, absent, canceled, expired or completed. The financial seal is separate from that pre-existing uncertainty barrier and never clears it.

Seals persist after denied approval, quote expiry, grant/key revocation, failed payment or success. No automatic unlock, retry with a new intent, cancellation release or remote mutation is allowed. This deliberately sacrifices liveness; future trusted resolution/release requires its own design. Failed quote transactions publish neither quote nor seal nor accepted result. At most one intent wins a source purchase, including concurrent callers.

Approval reuses the current native atomic attempt/challenge/replay/grant/reservation machinery, additionally validating the original external binding. It publishes no partial reservation/authority on failure. Every native-family guard in PaymentService, ExecutePayment and JdbcPaymentStore (expiry, execute, prepare, post-prepare and dispatch) must include the external profile explicitly; no legacy path fallback. Already financially ADMITTED/PENDING/UNKNOWN work remains owned by its original operation. Later expiry, configuration changes or authority revocation must not erase exposure, release an unresolved reservation, initiate another charge or block read-only reconciliation of the original operation.

## Failure contract

Use existing sanitized envelope and retry conventions. Invalid request/types are 400; missing scope/access follows existing 403/404 behavior. Unsupported profile/port/handler/registration is 422 UNSUPPORTED_CAPABILITY. Invalid source bytes/terms/artifacts are 422 AUTHORITY_BINDING_INVALID. Revision/current-response drift is 409 CHECKOUT_CHANGED; configuration drift is 409 CONFIGURATION_CHANGED; uncertainty is 409 CHECKOUT_MUTATION_BLOCKED; active command is 409 CHECKOUT_COMMAND_IN_FLIGHT; sealed/already-owned purchase is 409 CHECKOUT_ALREADY_BOUND. Expiry uses 410 AUTHORITY_EXPIRED. Accepted-key input drift uses 409 IDEMPOTENCY_CONFLICT. Existing revoked/replay failures retain their names. Temporary precommit storage/crypto availability uses sanitized 503/SAME_COMMAND. Never map an expected purchase-ownership conflict to AUTHORITY_REPLAY through a generic unique-constraint handler.

## Executable integration

The executable path is opt-in synthetic commerce HTTP create/retrieve -> external quote HTTP -> existing trusted UI approval -> existing synthetic execute/challenge/recovery HTTP. The commerce LangGraph/SQLite workflow can produce the selected safe observation, but the generic payment workflow must not silently accept this new profile: durable graph handoff needs immutable external-reference registration and is deferred. The HTTP journey plus existing UI is the end-to-end slice. No new framework/dependency or Google AP2 implementation is introduced.

## Testable acceptance

The independent acceptance plan must demonstrate these behaviors, beyond successful compilation:

1. Two supported external prices/currencies are derived from exact retained bytes and survive real HTTP, approval, restart, challenge and synthetic execution; retained response/artifact/JWS payload equality includes noncanonical whitespace/order. No /complete request, vendor execution or provider-journal admission occurs.
2. Missing registration/capability and old timestamp-less history fail closed. Native, legacy and lifecycle-only profiles preserve behavior. Replacement/decorated checkout, authority, artifact and lifecycle/admission implementations retain behavioral checks; defaults never silently support the new profile.
3. Malformed/duplicate/invalid UTF-8, fractions/overflow, inconsistent line/root totals, unknown handler/action/fields, wrong raw-versus-projection metadata, changed bytes/digests, wrong scope/principal/configuration/response and canceled/completed/non-ready states reject without financial mutation.
4. Shared-lock races cover two intents for one purchase, quote versus stage/claim, configuration changes and clock boundary; at most one lawful result commits. Unknown-create and recovered delayed update remain permanently ineligible after later GET and restart. No later worker can acquire a fresh send through the seal.
5. SQL and artifact/verification faults prove quote/seal/result rollback together and approval replay/grant/attempt/reservation rollback together. Accepted retries sign once and retain exact identities. Rejected access cannot expose replay data. Restart preserves the seal and verification from public enrollment/original artifacts.
6. Expiry at exact freshness/remote/grant boundaries, future observation and key/configuration revocation block new admission. Revocation/configuration changes after financially unknown dispatch preserve operation, exposure and original-key reconciliation; no duplicate effect or automatic release occurs.
7. Real PostgreSQL upgrade from V009 preserves old payment/lifecycle/provider history and migration checksums; old observations remain ineligible. Fresh/repeated migration works. A fresh-JVM reconstruction proves durable source/binding/authority preservation rather than merely reusing objects.
8. HTTP rejects unauthorized roles/merchants, altered idempotent input, unknown fields and raw/credential injection. Responses, logs, workflow state and evidence contain no protected bytes, keys, credentials or remote identifiers. Independent pinned-schema validation covers the financial-ready fixture.

Validation includes targeted checks and the documented PostgreSQL-backed aggregate conformance runner, documentation checks and whitespace check. Evidence names the exact profile and tested scope; NOT_CERTIFIED and remaining external/production obligations remain visible. No disabled/skipped integration checks may substitute for required evidence.

## Alternatives considered and consequences

Using SafeView or only responseReference as authority loses exact provenance and terms. Regenerating the native fixture loses the merchant observation and can authorize another amount. A read-then-write bridge across independent transactions races lifecycle/configuration changes. Allowing GET/update after quote requires a more complex invalidation/reapproval protocol. Treating remote completed as local payment success creates an ownership conflict. All are rejected for this slice.

Permanent sealing and explicit synthetic attestation yield a small auditable bridge, reuse independent AP2 verification and preserve one execution owner. They intentionally leave remote merchant authenticity, mutable live checkout semantics, release/requote policy, external graph handoff and production execution unresolved.
