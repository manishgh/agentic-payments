## Required security boundary

The enclosing PaymentIntent must bind AP2 authorization, one immutable merchant-signed ACP checkout, one subject/grant/budget reservation and one eventual financial operation. A valid protocol signature alone is not this binding. The application must reconstruct trusted expected facts from its authoritative checkout and enrollment state, verify the original artifacts inside its transaction boundary, and persist the authorization decision with the reservation and immutable attempt. An `Ap2Engine.Proof` value, caller-supplied expected facts or a prior process-local replay decision cannot authorize spending.

The local runtime may issue synthetic TAP mandates after authenticated trusted-UI approval. That establishes the configured synthetic assertion only. The graph must not issue consent, sign artifacts, select trust keys, complete customer authentication or infer payment truth from its checkpoint. The existing independently authored native engine remains separate from the database and provider adapters.

## Findings and accepted design dispositions

| ID | Risk | Required disposition |
| --- | --- | --- |
| DA-001 | Baseline intents have no stored profile; the old approval route can reserve without AP2. | Store an immutable exact profile per intent, backfill historical rows as legacy, reject the legacy approval implementation for AP2 intents and fail closed at dispatch when AP2 evidence is absent. A shared HTTP route must select only the persisted profile's implementation. |
| DA-002 | The baseline local checkout bytes are not an ACP CheckoutSession. Parsed equality also loses signed identity. | Store the original merchant-signed ACP artifact and exact payload bytes, pinned version, revision/session and separately derived authoritative scope. Validate the supported ACP structure and handler, and compare the exact compact JWT including its signature. |
| DA-003 | Public proof records and request-supplied amounts, merchant, keys or subjects can be fabricated. | Reverify raw retained artifacts using enrolled role-specific public keys and server-derived checkout/grant facts. Resolve the subject from trusted authenticated session and issued durable challenge; the selected mandate envelope does not carry a subject claim. |
| DA-004 | A run-scoped replay ledger admits the same authorization in another run; signature hashes admit alternative valid ECDSA signatures. | Atomically consume issued challenges and tenant/issuer/role/JWT identities across runs, excluding signature representation and caller nonce aliases from identity. Enforce uniqueness in PostgreSQL, because different run locks do not serialize. |
| DA-005 | A crash between replay consumption and reservation strands authority or permits a second spend. | Commit challenge consumption, replay identities, verified authority evidence, attempt, exact reservation, intent version and command result together. Any failure rolls all of them back. |
| DA-006 | Process-local keys, replay state or proof objects disappear on restart. | Retain exact artifacts, durable public-key enrollment and decision bindings. Restart must verify old artifacts without re-signing; private keys stay transient and out of database, graph and logs. New signing keys use distinct identities. |
| DA-007 | Approval or successful authentication can outlive the mandate, grant, checkout or key. | At dispatch admission recheck current durable trust, grant version/revocation, all authority/checkout expiry and immutable binding, plus the separate bound customer action and HELD reservation. Define a common lock order for mutable trust and financial state. |
| DA-008 | Rechecking expiry after financial admission can erase accepted exposure or provoke a replacement charge. | Only pre-admission authority failure may terminate and release. Once admitted, preserve the same execution owner, operation and idempotency identity, and reconcile authoritative provider facts regardless of later expiry/revocation. |
| DA-009 | Retried approval may generate fresh signatures or refresh consent; raw artifacts may enter command/evidence/checkpoint output. | Check scoped command replay before signing or issuing authority; exact retries return the original result, changed requests conflict. Use explicit safe response and graph allowlists, redacted representations and bounded errors. |
| DA-010 | Concrete AP2/ACP, crypto, storage, grant and transport choices can become inseparable runtime dependencies; generic plug-ins can appear replaceable while weakening financial invariants. | Define versioned behavioral ports with explicit capabilities, typed inputs/results, safe errors, ownership and conformance obligations across protocol and infrastructure boundaries. Support replacement, decoration and delegation through the same public composition contracts. Negotiate unsupported capabilities explicitly; no silent fallback. PostgreSQL atomic admission is a declared capability, not an implied property of arbitrary CRUD/blob stores. |
| DA-011 | LangGraph checkpointing can become the mandatory execution runtime, or nondeterministic graph/model effects can run inside a replaying durable orchestrator. | Separate graph decision logic from a stable durable-execution runtime port. Specify activity/command identities, signals, timers, retries, cancellation and recovery capabilities. A new Temporal, Cadence or Azure Durable Task backend is an adapter to that same port. Declare the local SQLite implementation's actual subset; do not claim compatibility from names. |

## Replaceability and composition requirements

The independent native AP2 and ACP implementations are reference adapters behind separate protocol contracts. A third-party ACP implementation can replace the reference adapter, or be wrapped/delegated to by it, without rewriting payment domain or admission code. This is a structural requirement for this slice, even though actual Stripe or other external connectors remain out of scope. The same principle applies to cryptographic operations/key services, signed-artifact storage, grants/replay/admission persistence and event transport.

Interfaces are stable and organized by responsibility, never by backend vendor. Adding an Azure, DynamoDB or remote grant-service backend requires an adapter and registration against the same applicable port; it must not require another vendor-specific interface or caller changes. Different responsibilities may have distinct contracts, such as immutable artifact storage versus atomic financial admission. Their guarantees remain vendor-neutral. Capability negotiation describes implementations of a stable contract, rather than multiplying interfaces for every implementation.

A contract must describe who owns each authoritative input, what has already been verified, exact profile/version and required capabilities, idempotency and durability semantics, error/retry behavior, and sensitive-output restrictions. Type compatibility alone is insufficient. A protocol result obtained from an untrusted caller is not interchangeable with a configured trusted adapter's verified result; a freely constructed proof record is never spending authority. A crypto provider cannot change the selected profile's algorithm, framing or enrolled-key policy by honoring untrusted token headers.

The admission transaction must remain one owner-controlled capability covering replay, grant/version checks, attempt and reservation. A replaceable remote grant service or artifact store may be usable only with a separately specified reservation/fencing or atomic-participation contract. This slice must neither advertise a distributed transaction it does not implement nor call independent remote writes inside the PostgreSQL transaction and claim rollback. A backend lacking a required capability must fail selection before authority is consumed or money exposed.

Durable execution owns scheduling and recovery, while LangGraph supplies decision logic. Nondeterministic graph/model work, random identifiers and network effects belong in explicitly scheduled activities, outside any deterministic replaying orchestrator. Activity identities and payment command keys must survive retries, signals and process reconstruction. The runtime may stop scheduling an activity, but cancellation cannot assert financial no effect, release UNKNOWN exposure or authorize a replacement operation. Core status and verified reconciliation remain authoritative. Protocol and business logic must not change when a conforming runtime adapter is registered.

## Implementation acceptance criteria and adversarial evidence

These are required future observations, not test results claimed by this design review.

1. A complete AP2-profile HTTP/UI/LangGraph path creates and quotes, stops for trusted consent, approves with durable native authority, prepares independently, stops for a separate customer challenge when required, admits once and settles from verified simulator evidence. Fresh graph processes resume the same identities using server status. No graph approval or customer-action role exists.
2. Validly signed wrong merchant, money, currency, instrument, checkout revision/session, audience, issuer, key role or nonce fails without consuming a challenge, creating an attempt or holding funds. A different valid checkout signature over identical JSON fails exact-artifact comparison. Duplicate/unsupported ACP fields and unconfigured handlers are refused rather than coerced.
3. Wrong subject, grant, tenant, run and old-profile approval requests fail. Supplying a forged proof, decoded claims, public key or an apparently successful protocol receipt cannot replace runtime verification. Successful preparation or customer authentication alone cannot authorize dispatch.
4. Concurrent duplicate approvals with different command keys yield one attempt and reservation. Concurrent same-JWT identities in distinct runs and a changed-valid-signature replay yield at most one authorization; new nonces/audiences do not bypass the identity guard. Competing valid approvals cannot exceed the exact budget. Database witnesses verify counts and amounts.
5. Inject failure after durable replay insertion but before reservation/command completion and prove full rollback. The unchanged valid authority can then succeed once. Kill/reconstruct after approval commit but before response and replay the same command: no new signature, deadline, grant, attempt, reservation or operation is created.
6. Before admission, race grant revocation, key revocation and exact half-open expiry against approval/dispatch with deterministic barriers. Both commit orders have defined results. Invalidating one authority component while waiting for customer action prevents dispatch and releases only unadmitted, undisputed exposure.
7. Restart the service between quote/approval, approval/preparation and authentication/admission. Persisted public keys and exact artifact references remain sufficient; graph restarts cannot alter authority. Missing or corrupted evidence is refused. There is no fallback to the legacy profile or regeneration of the approved checkout.
8. After admission, expire/revoke authority and lose the adapter response. Reconciliation uses the original operation, maintains HELD exposure while UNKNOWN and consumes exactly once on verified success. Extend existing abrupt-process recovery evidence to an AP2-profile admitted operation. The AP2 protocol exchange must never invoke an independent second financial executor.
9. Same idempotency key with changed semantic input conflicts. Exact replay after authority expiry returns the old command result subject to current object access, while authoritative status and fresh dispatch still enforce current pre-admission policy. An old approval result must not create a new consent decision or report a new admission.
10. Scan graph checkpoints, normal HTTP responses, audit/report/evidence output and process diagnostics with distinctive artifact/key/credential canaries. Exact signed artifacts stay solely in the trusted core store; private keys never persist. Safe hash/opaque identity metadata may leave the core. Existing legacy scenarios remain separately labeled and supported.
11. Exercise alternative and decorating/delegating fake implementations through the actual public composition interfaces, rather than replacing implementation internals. Prove reference AP2 and ACP adapters can be selected separately, ACP delegation preserves original artifact bytes and one execution owner, and crypto/store/grant/event boundaries are genuinely injected. The same behavioral contract tests apply to interchangeable implementations. Unsupported version, algorithm, trust, persistence, admission or transport capabilities fail explicitly before financial mutation; a generic storage implementation cannot masquerade as atomic replay-and-budget admission.
12. Run checkout, trusted approval, separate authentication pause, process crash, resume and reconciliation of the same operation through the durable-runtime contract. A replacement/decorator test preserves stable activity and command identities and refuses unsupported timers/signals/retry modes before execution. Replay must not run graph/model/network nondeterminism inline; duplicate signals/resumes cannot duplicate financial effects. Runtime cancellation during UNKNOWN preserves exposure and permits same-operation recovery. Explicitly distinguish the local SQLite adapter's implemented guarantees from deferred Temporal/Cadence/Azure integrations.

The integration owner must run the repository documentation checks, real-PostgreSQL integration tests and relevant HTTP/UI/workflow/conformance checks after independent source review. No Maven, application tests or runtime changes were performed by this reviewer during the design assessment.

## Scope limits

This gate concerns only a local synthetic direct-TAP AP2 profile with embedded pinned ACP checkout data and a simulator execution owner. It does not accept a real user enrollment/consent service, remote merchant ACP completion, external CP/MPP processing, 3DS, autonomous delegation, selective disclosures, full AP2 interoperability, deployment or certification. Additive schema/API changes are authorized for this slice; unsupported protocol/provider capabilities must still fail explicitly.
